# ADR-0016: Committed Flux manifests and a read-only deploy key; no `flux bootstrap`

**Status:** Accepted (Stage 0) · **Date:** 2026-10-13

## Context
`flux bootstrap <provider>` needs write access to the repository so it can commit its own manifests, and it creates deploy keys through the forge API. SPEC §4.9 says authority narrows toward production. Flux needs only read access.

## Decision
- The pinned Flux version's controller manifests (`gotk-components.yaml`) and sync objects are **committed** under `gitops/clusters/<cluster>/flux-system/`, generated by `flux install --export` inside the toolbox at a pinned version. A CI check (F11) regenerates them and fails on any diff.
- Flux reaches Forgejo through a **read-only deploy key** (`SC-FLUX-DEPLOY-KEY`) on `strange-company`, over the in-cluster SSH Service. The `known_hosts` entry is pinned from the Forgejo SSH host key that forge-init generates and records.
- Flux upgrades go through a PR that regenerates the committed manifests. Flux then upgrades itself.

## Consequences
No write credential exists in `flux-system`, and Flux upgrades are reviewable diffs.

## Alternatives rejected
- `flux bootstrap gitea`: it requires write access and a forge token.
- The Flux Operator: a viable later evolution, but it adds a component. Revisit post-MVP.

## Verification
F11 gate: regenerated manifests are identical to the committed ones. P06 gate: the deploy key on Forgejo has `read_only: true`, and Flux reconciles successfully.

## Amendments (Stage-0 consolidation)
- **2026-10-13, refined by ADR-0252.** The Forgejo SSH host key is **pre-generated by bootstrap before seed**, not by forge-init. It is stored SOPS-encrypted in the installation config, so the Flux `known_hosts` pin exists before Forgejo starts and survives a Forgejo rebuild or restore unchanged.
- **2026-10-13, plan 19 Q5.** The Flux source credential Secret is `flux-system/flux-system`. Its SOPS source file name is defined by plan 18 (`flux-source-auth.sops.yaml`).
