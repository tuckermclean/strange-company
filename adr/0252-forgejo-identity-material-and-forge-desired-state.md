# ADR-0252: Forgejo durable identity material is pre-generated in Git; forge configuration is a desired-state file; OIDC arrives by `valuesFrom` after transfer

**Status:** Accepted (Stage 0) · **Date:** 2026-10-13 · **Owning plan:** 16

## Context
Forgejo encrypts push-mirror credentials, 2FA secrets and OAuth2 application secrets with its `SECRET_KEY`. Its SSH host key is pinned in Flux's and workers' `known_hosts` (ADR-0016). If either is generated on the PVC at first start, losing the PVC (or black start) silently invalidates encrypted DB columns or breaks every SSH client. Forge objects that policy depends on (teams, bot membership, branch protection, webhooks, the push mirror) are normally created by clicking or by one-off API calls, which is not explainable by Git (SPEC §4.2, §4.7). Finally, the seeded Forgejo HelmRelease must not change at control transfer (ADR-0005), yet the OIDC source can only be registered once Authentik exists (after transfer).

## Decision
- **Pre-generated identity material:** `SECRET_KEY`, `INTERNAL_TOKEN`, `JWT_SECRET`, `LFS_JWT_SECRET` (`SC-FORGEJO-APP-SECRETS`) and the ed25519 SSH host key (`SC-FORGEJO-SSH-HOST-KEY`) are generated by the bootstrap orchestrator before seed, SOPS-encrypted in Git (both recipients; no bundle copy) and mounted by the HelmRelease. The Flux deploy key (`flux-source-auth.sops.yaml`, Secret `flux-system/flux-system`) and the Runner webhook secret are pre-seeded the same way; forge-init only registers them in Forgejo. forge-init *verifies and records* the host-key fingerprint; it never generates it. (Refines ADR-0016's wording, no change in intent.)
- **Forge desired state:** `forge/forge.yaml` (kind `ForgeConfiguration`) declares orgs, teams, bots and token scopes, deploy keys, branch protection stages, protected tags (`*`, `v*`, `sc-archive/*`, `sc-quarantine/*`), package cleanup rules, webhooks and push mirrors, validated by `contracts/forge-configuration.schema.yaml`. forge-init applies it at bootstrap. Afterwards `sc-bootstrap forge apply` (operator-run, diff first) applies reviewed changes, and `platform-probes` reports drift every 5 minutes (`SCForgeConfigDrift`). An in-cluster reconciler is post-MVP.
- **`sc-admin` is not a standing human credential (review AUTH-9).** The SOPS value only creates the account on an empty database (chart `initialOnlyNoReset`); `forge finalize` replaces it with a bundle-only value. Steady-state administration uses the operator's own admin identity or short-lived tokens minted with `kubectl exec … forgejo admin user generate-access-token`; any other `sc-admin` token raises `SCForgeUnexpectedAdminToken`.
- **Chart provenance (CD-26, supersedes CD-20).** No Bitnami image, repository or deployable chart; the template-only `common` library vendored in the forgejo-helm package is allowed when it is `type: library`.
- **Staged branch protection:** stage `bootstrap` whitelists `sc-admin` for direct pushes (forge-init outputs). Stage `steady` (applied at P12 finalize) removes every push whitelist entry and requires the status contexts whose producers exist. Stage `recovery` (Runner contexts removed, two approvals, admins still bound) is applied only by `forge apply --stage recovery` from `emergency-merge.md` (plan 55) when a merge-gate component is broken.
- **OIDC delivery:** the seeded HelmRelease carries `valuesFrom: [{kind: Secret, name: forgejo-oidc-values, optional: true}]` from the first commit. Plan 15 creates that Secret after Authentik is healthy, which triggers exactly one upgrade that registers the `authentik` source. The HelmRelease object itself never changes at transfer.

## Consequences
- Black start restores Forgejo with its original `SECRET_KEY` and host key, so the DB's encrypted columns stay readable and no `known_hosts` changes.
- `SECRET_KEY` is effectively non-rotatable in place (re-encryption is unsupported). A compromise requires re-creating encrypted credentials and re-enrolling 2FA.
- Forge configuration changes are PRs, and manual drift is visible but not auto-reverted in MVP.

## Alternatives rejected
- Letting the chart generate secrets on the PVC: lost with the PVC.
- forge-init generating the host key after seed: Forgejo would start once with a different key, and Flux `known_hosts` would depend on bootstrap ordering.
- Registering the OIDC source at seed: Forgejo would start with an unreachable discovery URL, and the HelmRelease would differ across the transfer.

## Verification
GATE-P04/P05 (plan 16): 16-AC-8 (host key is the pre-generated one), 16-AC-9 (`SECRET_KEY` from Git), 16-AC-17 (forge-init idempotent, zero mutations on re-run), 16-AC-18 and 16-AC-32 (staged protection), 16-AC-26 and 16-AC-31 (OIDC source registered post-transfer).
