## 1. Purpose

SPEC §5 makes `strange-company` simultaneously the bootstrap repository, infrastructure source, GitOps source, application source, specification, recovery seed and knowledge base. This plan fixes **where everything lives** so that 50+ plans, CI, Flux, the Runner and the bootstrap orchestrator agree on paths. It also defines:

- where every pinned version, digest and checksum lives, and how CI checks them;
- the Make target catalogue, which is the one interface CI products (GitHub Actions interim, Woodpecker later; ADR-0018) call;
- the role of `AGENTS.md` and of `.strange-company/` for this repository;
- branch and tag conventions and the protected paths of this repository;
- the installation directory `gitops/clusters/<cluster>/` and every other file that bootstrap generates and commits.

## 2. Requirements derived from SPEC.md

1. There is exactly one primary repository, `strange-company`; no separate bootstrap repository [SPEC §5].
2. The repository serves every role in SPEC §5 from one tree [SPEC §5, §6].
3. The operator flow `git clone … ; cp bootstrap.env.example bootstrap.env ; ./bootstrap --profile …` works from the repository root [SPEC §7, §130].
4. Tool versions are version-controlled [SPEC §9]. Production dependencies are pinned where practical, image references immutable [SPEC §37], critical images and dependencies pinned [SPEC §116].
5. Important policy (validation, TDD, exemptions, retries, routing, budgets, resource profiles, protected paths, branch and merge policy, context rules, security requirements) is version-controlled [SPEC §4.7].
6. Every managed repository supports durable repository context (`AGENTS.md`, `.strange-company/{repo.yaml,architecture.md,policy.yaml,validation.yaml,decisions/,roles/}`); this repository is a managed repository [SPEC §42].
7. `AGENTS.md` may instruct workers but is not enforcement [SPEC §4.4, §42, §58].
8. Agent branches are `agent/<task-id>`; workers never push protected branches [SPEC §100].
9. Company context lives in Git [SPEC §41].
10. Stage-0 structure (plans, procedures, contracts, adr, PLAN.md, STATUS.md) is preserved [SPEC §120].
11. Default project CI requires no paid model API [SPEC §104].
12. Bootstrap scratch state has a retention rule and never becomes authoritative [SPEC §4.1, §107].

Derived requirements:
- **01-R-1** Every path named by any plan resolves to exactly one location defined in §6.1. A path that is not in §6.1 is added here by PR before an implementation PR introduces it (`make layout-check`, §7.1).
- **01-R-2** Every third-party artifact that is executed or deployed (binary, image, chart, Go module, Python package, Ansible collection, OpenTofu provider plugin, GitHub Action) is pinned to an immutable identifier (sha256 digest, checksum, commit SHA or hash-locked version) in exactly one lock location (§6.3). `make locks-check` fails otherwise.
- **01-R-3** Every CI gate is a Make target that behaves identically on a laptop, on GitHub Actions and on Woodpecker, because it runs inside the pinned `ci` image (plan 02).
- **01-R-4** No file under the repository is generated by a tool at runtime *and* also edited by humans. Generated files carry a header `# GENERATED by <tool> — do not edit; regenerate with <make target>` and have a `*-check` target that regenerates and diffs.
- **01-R-5** Nothing secret is committed in plaintext. `bootstrap.env`, `.bootstrap/` and `out/` are gitignored, and `make secrets-scan` fails on known secret patterns and on any `*.sops.yaml` that is not SOPS-encrypted.

Rules:
- A directory exists only if a plan owns it. The owning plan for each top-level directory is recorded in `.strange-company/repo.yaml` `importantPaths[].description` ("owner: plan NN").
- `docs/` is not created. Operator documentation is `procedures/`; design documentation is `plans/` and `adr/`; reference notes go to `plans/reference/`.
- No symlinks anywhere in the tree except `toolbox/` build contexts if plan 02 requires none (it does not). `make layout-check` rejects symlinks (they break the seed snapshot integrity check, plan 19 §8.3, and Windows clones).
- Executable files are limited to `bootstrap`, files under `toolbox/bin/` and `test/e2e/**/run` (mode `100755`). Everything else is `100644` (`make layout-check`).

- `cmd/` holds only `main` packages. Library code lives in `src/internal/<area>/`. References in other plans to `src/runner/**` and `src/policy/**` mean `src/internal/runner/**` and `src/internal/policy/**` (reported for consolidation, §25).

- One module: a single `go.sum` and one dependency-update stream (Renovate, plan 23).

### 6.3 Version lock files (ADR-0106)

Every pinned identifier lives in exactly one of these files. Nothing else in the tree may contain a floating reference (`latest`, a bare tag without digest, a version range).

| Lock file | Content | Schema / format | Written by | Read by | Check |
|---|---|---|---|---|---|
| `versions/platform.lock.yaml` | Flux version; every Helm chart (`repo`/`oci` URL, chart name, exact version, OCI digest); every upstream container image used by GitOps manifests (`repository@sha256`); Kubernetes minor | `kind: PlatformVersionLock` (§8.2) | Renovate PR / human PR | `sc-gitops render` (plan 18), F11 checks | `locks-check`, `gitops-validate` |
| `versions/k3s.lock.yaml` | k3s version; sha256 of the k3s binary per arch (`amd64`; `arm64` optional); airgap image tarball sha256 (if used); `etcdctl` version + sha256; the `coredns` image digest rendered by plan 09 (bundled CoreDNS is replaced, plan 07 07-R-3) | `kind: K3sVersionLock` | Renovate / plan 48 upgrade PR | Ansible role `k3s` (plan 07) via `vars.json`, verify V-10 | `locks-check`; Kubernetes minor equals `platform.lock.yaml` `kubernetes.minor` |
| `versions/compat.yaml` | Supported Kubernetes minors per pinned component; recorded third-party behavior facts (e.g. `k3s.etcdLearnerJoin`) | `kind: CompatibilityMatrix` | human PR (plans 07, 48) | F11 (plan 18), plan 48 upgrade gate | `locks-check`: pinned Kubernetes minor ∈ every component's supported set |
| `versions/internal-images.lock.yaml` | digests of Strange Company images (agent-runner, model-gateway, sc-verify, sc-worker base, fake harness) at the last release | `kind: InternalImageLock` | release pipeline PR (plan 23) | chart values rendering (plan 54), V-26 | `locks-check`: every entry has `@sha256:` |
| `toolbox/tools.lock.yaml` | every toolbox and ci-image tool: version, download URL template, sha256 per arch, version command + expected regex; base image digests; Debian snapshot timestamp | `kind: ToolboxLock` (plan 02 §9.2) | Renovate / human PR | `toolbox/Containerfile` build, PF-01 self-check | `toolbox-check`, `locks-check` |
| `toolbox/requirements.txt` | Python packages for Ansible in the toolbox, `--hash=sha256:` per wheel/sdist | pip hash-checking mode | `pip-compile --generate-hashes` in the ci image (`make toolbox-pydeps`) | toolbox build | build fails on missing hash |
| `toolbox/image.lock` | published toolbox and ci image index digests + the toolbox inputs id they were built from | `kind: ToolboxImageLock` (plan 02 §9.3) | release pipeline PR (plan 23) | `./bootstrap` wrapper | `toolbox-check` |
| `infra/tofu/**/.terraform.lock.hcl` | OpenTofu provider plugin versions + hashes for `linux_amd64` and `linux_arm64` | OpenTofu native | `make tofu-lock` (runs `tofu providers lock -platform=linux_amd64 -platform=linux_arm64`) | every `tofu init -lockfile=readonly` (plan 06) | `tofu-validate` |
| `src/go.mod` + `src/go.sum` | Go module requirements and checksums; Go toolchain (`go` and `toolchain` directives) | Go native | `go get` in a PR | `go build` with `GOFLAGS=-mod=readonly`, `GOSUMDB` default | `make lint` runs `go mod verify` and `go mod tidy -diff` |
| `policy/harnesses.yaml` | harness image digests (SPEC §63) | `contracts/harness.schema.yaml` | plan 28 PRs | Runner | `policy-check`; `locks-check` greps for `@sha256:` |
| `.github/workflows/*.yaml`, `.woodpecker/*.yaml` | action references pinned by full commit SHA; pipeline step images pinned by digest | native | plan 52 PRs | CI | `locks-check` (`uses: owner/repo@<40-hex>` only; `image: …@sha256:` only) |
| `versions/lab-images.lock.yaml` | lab VM cloud images (Debian 13 genericcloud, Ubuntu 24.04 cloud image) per arch: URL, upstream checksum (sha512 for Debian, sha256 for Ubuntu), image build serial | `kind: LabImageLock` | Renovate / human PR | `sc-lab` (plan 05 §14.6) | `locks-check` |
| `infra/catalog/prices/*.yaml` | infrastructure prices (not versions, but version-controlled facts with `verifiedAt`) | `InfraPriceCatalog` | human PR | plan 03 guard | `locks-check` (version bump rule, plan 03 §14.5) |

**Versions** come from `plans/compatibility-baseline.yaml` (CD-29, ADR-0022): every pin lies inside its component's baseline line; moving to a newer minor or major is a plan-amendment PR that also updates the baseline. This plan states the mechanics only:
- A lock entry records `version`, the immutable identifier, `selectedBy` (`baseline:<component>`, the baseline entry the pin belongs to, e.g. `baseline:flux`) and `verifiedAt` (date of the last re-verification test run for version-sensitive behavior).
- Renovate (plan 23) is configured with custom regex managers for every file above, so every update arrives as a PR that runs the full catalogue.
- `make locks-check` (implemented in `sc-lint locks`) asserts, deterministically and offline:
  1. every lock file validates against its kind's schema;
  2. no floating references anywhere in `gitops/`, `charts/`, `toolbox/`, `images/`, `harnesses/`, `.woodpecker/`, `.github/workflows/`, `infra/` (regex scan: image references must contain `@sha256:[0-9a-f]{64}`; Helm chart versions must be exact semver; GitHub Actions `uses:` must be a 40-hex SHA);
  3. cross-file consistency: `platform.lock.yaml` `flux.version` = Flux CLI version in `toolbox/tools.lock.yaml`; Kubernetes minor of `k3s.lock.yaml` = `platform.lock.yaml` `kubernetes.minor` = kubectl minor in `tools.lock.yaml` (skew 0); `compat.yaml` lists that minor as supported for every pinned component;
  4. every chart and image referenced by rendered manifests appears in `platform.lock.yaml` (via `sc-gitops inventory`, plan 18);
  5. `metadata.version` of a changed `infra/catalog/prices/*.yaml` increased versus the merge base (plan 03 §14.5).
- Online re-verification (does the digest still exist upstream? does the checksum still match the download?) is `make locks-verify-online`, run nightly by plan 52, never a PR gate (network flakiness must not block merges).

`versions.lock` as written in plans 18 and 19 denotes `versions/platform.lock.yaml` (reported, §25).

### 6.4 Branches, tags and commit conventions (this repository)

| Ref | Purpose | Who may push | Protection (plan 55 implements in Forgejo; plan 17 on GitHub) |
|---|---|---|---|
| `main` | only long-lived integration branch; Flux source (ADR-0016) | nobody directly after control transfer; merges through PR by a human (ADR-0019) | protected: PR required, required statuses (plan 55), ≥1 approval, no force-push, no deletion, deploy keys cannot push |
| `release/v<major>.<minor>` | release maintenance branches (plan 23), created only when a patch is needed on an older minor | merge via PR | same as `main` |
| tags `v<major>.<minor>.<patch>` | annotated release tags (PF-05 checks); created by the release pipeline (plan 23) | release identity only | protected tags; no deletion, no move |
| `agent/<task-id>` | worker output (SPEC §100); `<task-id>` = `sc-<n>` | the execution's deploy key (ADR-0007) | unprotected; Runner detects pushes elsewhere (ADR-0007) |
| `bootstrap/<purpose>-<run-id>` | post-transfer config changes opened as PRs by sc-bootstrap (plan 50 §14.10, 50-R-5), e.g. `bootstrap/expand-20261013T101500Z-a1b2` | `sc-admin` during bootstrap/expand | unprotected; PR into `main` |
| `renovate/<manager>-<dep>` | dependency updates (plan 23) | `sc-renovate` | unprotected |
| `sc-verify/push-probe-<run-id>` | transient push probe of `./bootstrap verify` (plan 50 V-03 = plan 19 C3), deleted within the same run | `sc-admin` | unprotected |
| `human/<user>/<topic>` | recommended prefix for human work branches | the human | unprotected; any non-reserved name is allowed for humans |

Reserved prefixes (`agent/`, `bootstrap/`, `renovate/`, `sc-verify/`, `release/`) may not be used by humans; plan 55's forge workflow treats PRs from them by their prefix. Reserved prefixes are listed in `.strange-company/policy.yaml` `reservedBranchPrefixes` (field name per plan 22's schema).

Commit conventions:
- Conventional subjects (`feat:`, `fix:`, `test(<task-id>):`, `docs:`, `chore:`, `build:`, `ci:`, `refactor:`, `bootstrap(<cluster>):`). `test(<task-id>): …` is reserved for RED test commits (master plan §6.1). `bootstrap(<cluster>): …` is reserved for sc-bootstrap commits (plan 50 §14.3), which carry trailers `SC-Install-Uid:` and `SC-Run-Id:`.
- Trailers used by checks: `SC-Task: sc-<n>` (Runner-created commits), `GitOps-Allow-Destroy: <kind>/<ns>/<name>` (plan 18 §8.6), `Co-Authored-By:` (allowed).
- `make commit-lint` (§7.1) checks subjects of the PR's commits against these patterns. It is advisory on human PRs in MVP (warn) and required on `agent/*` and `bootstrap/*` PRs (plan 55 decides the required set).

**Before control transfer** (Phase 1, ADR-0018) GitHub is the origin and `main` there is protected the same way (PR, required interim-CI status, ≥1 approval). After transfer GitHub is read-only except for the mirror credential (SI-11, plan 17).

- `<cluster>` is the `CLUSTER_NAME` (pattern `^[a-z][a-z0-9-]{1,30}[a-z0-9]$`). Plan 35's register writes `secrets/offcluster/{install}/`; `{install}` there **is** the cluster name (reported, §25).

### 8.3 Contract tooling (F02)

`sc-contracts` (Go, `src/cmd/sc-contracts`) is the single contract validator:
- For each `contracts/*.schema.yaml`: parse YAML (1.2 core schema; duplicate keys are an error), check `$schema` = 2020-12, `$id` = `https://strange.company/contracts/<file-stem>/v1alpha1`, `title`, `description`, ≥ 1 `examples`; meta-validate; validate each `examples[i]` (must pass), each `x-invalid-examples[i].value` (must fail, and `reason` present), each `x-defs-examples.<Def>[i]` against `#/$defs/<Def>`.
- For `contracts/*.openapi.yaml`: OpenAPI 3.1 structural validation, every `$ref` resolves, every schema example validates.
- Register files (`contracts/*.yaml` without `.schema`) validate against their companion schema (`alert-catalog.yaml` → `alert-catalog.schema.yaml`, `secret-classes.yaml` → `secret-classes.schema.yaml`; mapping by `kind` + file stem, declared by the `kind`/file-stem table below).
- **Instance validation:** every repository file of a contract-governed kind validates against its schema. There is no separate index file: `sc-contracts` selects the schema from the file's `apiVersion: strange.company/v1alpha1` + `kind` (each schema's top level or `$defs` entry carries `kind: {const: …}`), and files without `kind` are mapped by the fixed globs below. A YAML file under the governed globs with an unknown `kind` fails (`CONTRACT_KIND_UNKNOWN`).

## 13. Security boundary

## 16. Retry behavior

Targets do not retry internally except network fetches in cache-warming targets (`gitops-cache`, `go mod download`): 3 attempts, 5 s/15 s backoff. Flaky tests are not retried; a flaky test is a bug (plan 52 policy).

## 17. Idempotency behavior

All targets are re-runnable; `fmt` and generators produce byte-identical output on rerun (01-R-4). Generated installation files are reproducible from the bundle (plan 50 §14.3 done check).

## 18. Bootstrap behavior

The operator needs only the clone. `./bootstrap` resolves the toolbox (plan 02) and never requires host `make`. Bootstrap-generated commits follow §6.5.

## 19. Upgrade behavior

- Layout changes are PRs that update this plan first, then `layout-check` fixtures.
- Lock updates arrive via Renovate PRs; version-sensitive behaviors are re-verified by the owning plans' acceptance tests that `verifiedAt` refers to.
- Go toolchain bumps change `go.mod` `toolchain` and `tools.lock.yaml` together (`locks-check` cross-check).

## 20. Recovery behavior

The repository is recovered from GitHub (black start, plan 45) or Forgejo bundles (plan 44). Nothing in this plan holds state that is not in Git. `.cache/`, `out/` and `.bootstrap/` are disposable (the latter is reconstructed from the S3 journal, plan 50 §20).

## 21. Observability

CI results (JUnit, `out/verify/summary.json`) are the observable output. Nightly `locks-verify-online` failures are notified by plan 52's CI notification path. No runtime metrics.

## 22. Testing strategy

- Each check in `sc-lint` has positive and negative fixtures under `src/internal/lint/testdata/` (one violating tree per rule).
- `sc-contracts` has fixtures for: wrong `$id`, missing examples, an invalid example that passes (must fail the check), a valid example that fails, a duplicate YAML key, a format violation.
- Make re-exec is tested by running `make -n verify` with and without `SC_IN_CONTAINER` and asserting the command lines.
- The tier-V offline property is tested once per CI image change (01-AC-6).
