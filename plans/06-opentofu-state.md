## 1. Purpose

This plan makes OpenTofu state survive the loss of the machine running bootstrap and the loss of the cluster it describes (SPEC §15). It defines the root-module topology, the S3 backend with native locking, mandatory state and plan encryption, who creates the state bucket, the one-time migration from local to remote state, the conformance test that proves an operator's S3 provider can actually lock, key rotation, and the restore and recovery paths that need nothing from the cluster.

## 2. Requirements derived from SPEC.md

1. State survives loss of the machine executing bootstrap [SPEC §15].
2. Temporary local state exists only until remote state can be initialized [SPEC §15].
3. Persistent state lives outside the cluster in S3-compatible object storage [SPEC §15, §29].
4. Versioning, locking, encryption, restricted credentials and a recovery procedure [SPEC §15].
5. State-encryption material is black-start material [SPEC §15, §111].
6. State recovery does not require the cluster being recovered [SPEC §15].
7. RPO = latest successful mutation; RTO ≤ 2 h [SPEC §108].
8. Repeatable restore testing exists for OpenTofu state, and its failure is visible and alertable [SPEC §109].
9. Destroying compute does not destroy remote state history [SPEC §114].
10. Procedure "OpenTofu state recovery" [SPEC §113].

Derived requirements:
- **06-R-1** Locking is *tested*, not assumed. If the operator's S3 provider does not reject a conditional create of an existing key, bootstrap fails closed before any state is stored remotely.
- **06-R-2** Encryption is `enforced` for state and plan. An unencrypted state or plan is never read or written, not even by mistake.
- **06-R-3** The state bucket and every recovery bucket are protected against deletion by sc-bootstrap in two independent ways: the storage guard forbids `delete` (plan 03 §14.4), and `prevent_destroy` is set on each bucket resource.
- **06-R-4** No OpenTofu state, state credential or state passphrase is present in the cluster. The in-cluster restore-test signal reads only a non-secret result object and structural metadata (§21, ADR-0100).

- Root-module sources `infra/tofu/storage/`, `infra/tofu/compute/<module>/` with committed `.terraform.lock.hcl`.

## 4. Outputs

- Remote state objects: `s3://<prefix>-tofu-state/<cluster>/storage/terraform.tfstate` and `s3://<prefix>-tofu-state/<cluster>/compute/terraform.tfstate`, plus transient lock objects `<key>.tflock`.
- A conformance result (`.bootstrap/runs/<run-id>/s3-conformance.json`, uploaded alongside the run).
- State verify results at `s3://<prefix>-tofu-state/<cluster>/restore-tests/<timestamp>.json` (`restore-test-result.schema.yaml`, plan 44; `test_id: rt-tofu-state`, `test_kind: opentofu-state`, `subject: opentofu-state`, `outcome: passed|failed`).


### 7.2 `./bootstrap state` subcommands (CLI owned by plan 50; semantics here)

| Command | Behavior |
|---|---|
| `state status` | Per root module: object exists, current version id, last-modified, serial, lineage, lock object present (holder info) — no decryption needed except for serial/lineage, which prompts for the passphrase |
| `state versions --module M [--limit N]` | Lists object versions newest first with version id, time, size; with the passphrase, also serial, lineage and resource count per version |
| `state restore --module M --version-id V` | Decrypts version V in memory, validates it (§20.2), then makes it current by server-side copy of that version onto the same key (new version; history preserved). Requires typed confirmation `restore <cluster> <module> <V[0:8]>` |
| `state unlock --module M` | Shows `<key>.tflock` content; after typed confirmation `unlock <cluster> <module>` runs `tofu force-unlock -force <LockID>` in the module's work dir |
| `state verify` | The full restore test (§20.1); writes a result object; exit 0/1 |
| `state import --module compute` | Generates OpenTofu `import` blocks from `OrphanScan` (plan 03) results into the work dir, plans, shows the plan (must be imports only), confirms, applies |

### 7.3 Backend and encryption configuration (illustrative, rendered by sc-bootstrap into the module work dir)

```hcl
terraform {
  backend "s3" {
    bucket                      = "<prefix>-tofu-state"
    key                         = "<cluster>/compute/terraform.tfstate"
    region                      = "<S3_REGION>"
    endpoints                   = { s3 = "<S3_ENDPOINT>" }   # (verify key name)
    use_path_style              = <S3_FORCE_PATH_STYLE>
    use_lockfile                = true                        # baseline OpenTofu v1.13.1 (verify)
    skip_credentials_validation = true                        # non-AWS endpoints (verify)
    skip_region_validation      = true
    skip_requesting_account_id  = true
    skip_metadata_api_check     = true
    skip_s3_checksum            = <from conformance test>     # some S3-compatibles reject new checksum headers (verify)
  }
}
```

Encryption is supplied through the `TF_ENCRYPTION` environment variable (verify), which holds HCL equivalent to:

```hcl
key_provider "pbkdf2" "p<N>" { passphrase = "<SC-TOFU-ENCRYPTION>" }   # ≥16 chars; we generate 43
method "aes_gcm" "p<N>"      { keys = key_provider.pbkdf2.p<N> }
state { method = method.aes_gcm.p<N>  enforced = true }
plan  { method = method.aes_gcm.p<N>  enforced = true }
```

`<N>` is the passphrase's generation (the bundle entry generation of that `SC-TOFU-ENCRYPTION` value; the first passphrase is `p1`). The names are stable per passphrase and never renamed: OpenTofu records the key provider's name in the encrypted state's metadata, so renaming a passphrase's provider (for example from `current` to `previous`) makes fallback decryption of existing state fail (verified with OpenTofu 1.13.1 during F08). During a rotation `TF_ENCRYPTION` additionally carries the previous passphrase's `key_provider "pbkdf2" "p<N-1>"` and `method "aes_gcm" "p<N-1>"`, and `fallback { method = method.aes_gcm.p<N-1> }` in both `state` and `plan` (§20.3). The bundle's instance names `current` and `previous` (06-AC-6) are independent of these provider names. The passphrase therefore never appears on disk, in files under `.bootstrap/` or in process arguments. It appears only in the environment of the `tofu` subprocess inside the container.

## 9. Configuration

| Knob | Source | Default | Notes |
|---|---|---|---|
| `S3_BUCKET_MODE` | `bootstrap.env` | `create` | `create`: the `storage` root module creates the plan 14 bucket set. `existing`: the operator pre-created them; sc-bootstrap only verifies (PF-12). Use `existing` when the S3 provider's bucket-creation API is not supported by the OpenTofu AWS provider or credentials lack `CreateBucket` |
| State bucket name | derived | `<S3_BUCKET_PREFIX>-tofu-state` | plan 14 is authoritative for names |
| OpenTofu version | `toolbox/tools.lock.yaml` | baseline: OpenTofu v1.13.1, line 1.13.x (`plans/compatibility-baseline.yaml`) | S3 `use_lockfile`, `endpoints.s3`, state encryption `pbkdf2` + `aes_gcm` + `fallback`, `TF_ENCRYPTION` env and the `encrypted_data` envelope re-verified at the baseline version by 06-AC-1..4 (verify) |
| AWS (S3) provider version for `storage` | `infra/tofu/storage/.terraform.lock.hcl` | baseline: hashicorp/aws v6.69.0, line 6.x (via registry.opentofu.org) | used only for `aws_s3_bucket*` (and plan 14's IAM resources) against the custom endpoint; endpoint override re-verified at the baseline version (verify) |
| Noncurrent-version retention for `tofu-state` | plan 14 bucket definition | noncurrent versions expire after **365 days** (plan 14 `infra/objstore/buckets.yaml`, plan 43); current versions never expire | stricter than plan 43's general default because state history is recovery data; passphrase rotation keeps the previous passphrase for the same 365 days (§20.3) |
| Lock timeout | sc-bootstrap | `-lock-timeout=60s` | longer waits surface as `TOFU_STATE_LOCKED` |

**Decision: who creates the state bucket (ADR-0100).** In `create` mode, sc-bootstrap's `storage` root module creates **all** plan 14 buckets, including `<prefix>-tofu-state`. It runs first with a local, encrypted state and then migrates its own state into the bucket it just created. Compute resources live in a **separate** `compute` root module that only ever uses the remote backend. Rationale: buckets have a recovery lifecycle and compute has a disposable lifecycle (SPEC §114). Two root modules make "destroy compute" structurally unable to plan a bucket deletion. Bucket contents and policies (`infra/tofu/modules/buckets`) belong to plan 14. The root module wiring, backend, encryption, `prevent_destroy` and migration belong to this plan.

| Class | Use here | Location |
|---|---|---|

Restricted credentials (SPEC §15): after `plan.storage-apply`, sc-bootstrap uses the `tofu-state` credential for every backend operation. `admin` is used only for the storage module itself. Plan 14 defines the policies.

## 11. Storage

- S3 as in §7.1. Bucket requirements, which plan 14 must satisfy and PF-12 and conformance verify: versioning `Enabled`; object lock not required; server-side encryption optional (state is already client-side encrypted); public access blocked.
- Local: `.bootstrap/work/<module>/` (working dirs, provider plugin cache `.bootstrap/work/.plugin-cache`), and the transient local storage state `.bootstrap/work/storage.local.tfstate` (encrypted), deleted after migration (§14.4).

## 12. Resource requirements

Negligible. State objects are < 1 MiB. Conformance uses < 100 KiB of objects for < 60 s.

## 13. Security boundary

- State is client-side encrypted (AES-GCM, pbkdf2 key) before upload. An S3 provider compromise exposes ciphertext and object metadata only.
- Who can decrypt: whoever holds the bundle plus its passphrase (operator). The cluster cannot.
- Who can delete history: only credentials with `DeleteObjectVersion` or bucket admin rights. `tofu-state` must not hold `DeleteObjectVersion` (plan 14). `admin` can, and it is held only by the operator.
- State must not contain provider secrets (plan 03 §10: sensitive and ephemeral variables, `do_not_send_password`).

## 14. Happy path

### 14.1 Order in the install pipeline (plan 50 §14.3)

Plan 50 §14.3's step table is authoritative (BOOT-10): `plan.install-identity` (passphrase generated) → `plan.storage-confirm` → `plan.storage-apply` (`admin`) → `plan.bundle-upload` → `plan.storage-credentials` (mints `tofu-state`) → `plan.objstore-capabilities` → `plan.state-conformance` (`tofu-state`) → `plan.state-migrate` (`tofu-state`) → `plan.bundle-confirm` → `plan.compute-plan` (remote backend) → `provision`.

### 14.2 `plan.storage-apply` (create mode)

1. `PrepareWorkdir(storage)` + `InitLocal`.
2. `tofu plan -out` with variables (prefix, cluster, region, endpoint, bucket set from plan 14).
3. Guard (`infra/tofu/storage/guard.yaml`): bucket resources `aws_s3_bucket`, `aws_s3_bucket_versioning`, `aws_s3_bucket_lifecycle_configuration`, `aws_s3_bucket_public_access_block`, `aws_s3_bucket_policy`, plus Object Lock (`aws_s3_bucket_object_lock_configuration`), server-side encryption (`aws_s3_bucket_server_side_encryption_configuration`) and the IAM/credential resources of plan 14's provider adapters (e.g. `aws_iam_user`, `aws_iam_user_policy` for `S3_PROVIDER=aws`; no `aws_iam_access_key`: keys are minted by plan 14's `EnsureCredentials` outside state so no secret lands in state, BOOT-18; the OVH S3-user and policy resources for `ovh`, verify names at plan 14 implementation). All `paid: false`, `allowedActions` without `delete`, count ≤ plan 14's bucket and instance counts. Plan 14 finalizes the list per adapter.
4. `tofu apply <planfile>`.
5. *Done check:* each bucket exists (HeadBucket 200) and versioning is `Enabled`. Partial creation is safe to resume, because OpenTofu re-plans only the missing resources.

Existing mode: steps 1–4 are skipped and step 5 runs as the check. On failure: `BUCKET_MISSING` or `BUCKET_VERSIONING_DISABLED` (exit 3).

Each bucket resource carries `lifecycle { prevent_destroy = true }`. `make tofu-validate` asserts that every `aws_s3_bucket` in the repo has it (static HCL check).

### 14.3 `plan.state-conformance` (06-R-1)

Run against `s3://<prefix>-tofu-state/<cluster>/conformance/<run-id>/` with the `tofu-state` credential:

| # | Test | Pass condition | Failure code |
|---|---|---|---|
| C1 | `PUT k1` with `If-None-Match: *` (absent key) | 200 | `S3_CONDITIONAL_PUT_UNSUPPORTED` |
| C2 | `PUT k1` again with `If-None-Match: *` | **412 Precondition Failed** (409 accepted only if the provider documents it (verify)) | `PF_S3_LOCK_UNSUPPORTED` |
| C3 | 8 concurrent `PUT k2 If-None-Match: *` | exactly 1 success, 7 × 412 | `PF_S3_LOCK_UNSUPPORTED` |
| C4 | `PUT k3` twice (unconditional), `ListObjectVersions k3` | ≥ 2 versions; `GET k3?versionId=<first>` returns the first content | `S3_VERSIONING_UNSUPPORTED` |
| C5 | `PUT k4 If-Match: <etag>` correct, then wrong etag | 200 then 412 → records `if_match_supported=true`; otherwise false (not fatal; plan 50 falls back to fixed leases) | — |
| C6 | Default PUT with SDK checksums, then with checksums disabled | records whether `skip_s3_checksum` is needed | `S3_CHECKSUM_INCOMPATIBLE` only if both fail |
| C7 | OpenTofu end-to-end: scratch module (no resources) with backend key `<cluster>/conformance/<run-id>/tofu.tfstate`. Write a lock file `tofu.tfstate.tflock` by hand (C1 semantics), then run `tofu plan -lock-timeout=0s` | tofu fails with a state lock error naming the hand-written lock ID | `TOFU_LOCKFILE_NOT_HONORED` |
| C8 | Server `Date` vs local clock | skew ≤ 60 s | `S3_CLOCK_SKEW` |

After the run, every object version under the conformance prefix is deleted (`DeleteObjectVersion` with `admin`). The result JSON records each test, latency and the derived flags (`if_match_supported`, `skip_s3_checksum`). Any fatal code fails the step and is surfaced as PF-14, with `procedures/bootstrap-preflight-failure.md#s3-locking`. There is **no override**. An S3 provider that cannot lock is unsupported for state (06-R-1).

### 14.4 `plan.state-migrate` (storage module only)

1. `tofu state list` (local) → set A.
2. Rewrite `_backend.tf` to s3 (§7.3) and run `tofu init -migrate-state -force-copy -input=false`.
3. `tofu state list` (remote) → set B. Require A = B, a remote object version id present, and `tofu plan` showing 0 changes.
4. Delete `.bootstrap/work/storage.local.tfstate*`. Record the remote version id in the journal.

*Done check:* the remote object exists, decrypts, and has the same address set. A local file, if any, is deleted after re-verification. A crash between steps 2 and 4 is safe: the remote copy exists, and the rerun goes through the done check and deletion.

The compute module never had local state. Its first `tofu init` targets s3 directly.

### 14.5 Normal operations

Every OpenTofu invocation runs in a fresh work dir, with the `TF_ENCRYPTION` and backend credentials in its environment, `-input=false`, `-lock-timeout=60s` and `-lockfile=readonly`. Plans are saved with `-out` (encrypted by the plan method) and applied exactly as planned (plan 03).

## 15. Failure modes

| Failure | Detection | Effect | Automated response | Procedure |
|---|---|---|---|---|
| S3 provider cannot lock | conformance C2/C3/C7 | no remote state | fail closed (exit 3) | bootstrap-preflight-failure.md#s3-locking |
| Versioning unsupported or disabled | C4 / PF-12 | no history | fail closed | bootstrap-preflight-failure.md#s3-locking |
| Stale `.tflock` (holder crashed) | `TOFU_STATE_LOCKED` after 60 s | phase blocked | report holder info; no auto-unlock | recover-opentofu-state.md#stale-lock |
| Latest state version corrupt / wrong lineage | decrypt or JSON parse fails, lineage ≠ journal | cannot plan | fail `TOFU_STATE_INVALID` | recover-opentofu-state.md#restore-version |
| Wrong passphrase | decrypt error | cannot plan | exit 8 | recover-opentofu-state.md#lost-passphrase |
| Passphrase lost (bundle + passphrase gone) | — | state unreadable | none | recover-opentofu-state.md#lost-passphrase (rebuild by import) |
| State object deleted (current version) | 404 with versions present | cannot plan | fail `TOFU_STATE_MISSING` | recover-opentofu-state.md#restore-version |
| Bucket deleted entirely | 404 NoSuchBucket | history lost | fail | recover-opentofu-state.md#rebuild-by-import |
| State drift (resource changed outside OpenTofu) | `plan` shows changes on re-run | guard may refuse (replace) | report | recover-opentofu-state.md#drift |
| Object-storage outage | S3 5xx/timeouts | no provisioning/expand/destroy; cluster unaffected | transient retries then fail | object-storage-outage.md (plan 14) |
| Concurrent apply from two machines | OpenTofu lock + plan 50 run lock | second refused | — | bootstrap-resume.md#lock |
| Encrypted state accidentally replaced with plaintext | `enforced = true` makes tofu refuse to read it | blocked | fail | recover-opentofu-state.md#restore-version |
| Restore test overdue / failed | in-cluster check (§21) | alert | `SCTofuStateRestoreTestFailed` | recover-opentofu-state.md#restore-test |

## 16. Retry behavior

S3 transient errors (5xx, timeouts, `SlowDown`) are retried by the SDK and OpenTofu, and then by plan 50 step retries. Lock contention is not retried beyond `-lock-timeout=60s`. Conformance failures are permanent.

## 17. Idempotency behavior

- `storage-apply`: plan/apply converge, and a rerun with all buckets present yields 0 changes.
- `state-migrate`: done check by remote existence plus an equal address set.
- `state restore`: restoring the version that is already current is a no-op (detected by comparing content digests).
- `state verify`: read-only apart from writing its result object.

## 18. Bootstrap behavior

The temporary local state exists only for the `storage` root module, only between `plan.storage-apply` and `plan.state-migrate`, in the same run if possible, and always encrypted (SPEC §15). In `existing` mode there is no local state at all.

## 19. Upgrade behavior

- OpenTofu upgrades: toolbox lock PR (plan 02). State format upgrades are performed by OpenTofu on the next write. Before merging an OpenTofu major or minor bump, `make tofu-validate` runs conformance C7 against the `s3-emulator` (ADR-0205) and plan-only runs against the guard fixtures (plan 03 §22).
- AWS or OVH provider plugin upgrades go through `.terraform.lock.hcl` PRs with `tofu providers lock -platform=linux_amd64 -platform=linux_arm64`.
- Encryption method changes (e.g. a new key provider) use the fallback mechanism, exactly like passphrase rotation (§20.3).

## 20. Recovery behavior

### 20.1 Restore test (`./bootstrap state verify`; SPEC §109)

For each module that exists for this installation (BOOT-4): `storage` iff bucket mode `create`; `compute` iff the provider uses OpenTofu (`ProviderOutput.tofu != null`); `edge` if present. The set is recorded in the journal and in the result (`modules`). An installation with `PROVIDER=existing` and `S3_BUCKET_MODE=existing` has no module: the result has `modules: []`, `outcome: passed` and one check `state-not-applicable`, so V-33 and RT-5 pass:
1. Download the current version and the newest noncurrent version into memory.
2. Decrypt both with the passphrase from the bundle (and the previous passphrase while a rotation fallback is active).
3. Validate JSON: lineage equals the journal's recorded lineage, serial is monotonic between the two versions, and resource addresses ⊇ the provider output's node resources.
4. Run `tofu plan -refresh=false` in a scratch work dir against a *copy* (local backend, encrypted) of the current version, and expect success.
5. Write a `restore-test-result` (plan 44 schema: `test_id: rt-tofu-state`, `test_kind: opentofu-state`, `subject: opentofu-state`, `outcome: passed|failed`, checks with per-step outcomes, evidence: version ids, serials, durations; no secrets) to `restore-tests/<ts>.json`.

It is run automatically by bootstrap `verify` (V-33) and by `expand`, `destroy` (pre-check) and `recover`, and manually monthly per the reminder alert.

### 20.2 Restoring a previous version

`./bootstrap state versions --module compute` → choose the newest version whose decrypt and validation pass → `./bootstrap state restore --module compute --version-id V`. A server-side copy creates a new current version, so history keeps growing. Afterwards, `tofu plan` shows drift between the restored state and reality. The operator resolves it with `-refresh-only` apply or import (procedure).

### 20.3 Passphrase rotation (`./bootstrap rotate tofu-passphrase`)

1. Open the bundle. Generate a new passphrase P2 (keeping P1).
2. Build `TF_ENCRYPTION` with P2 as the enforced method (key provider `p<N+1>`, where P1 is `p<N>`) and P1 as the fallback (key provider `p<N>`, unchanged name) for state and plan (§7.3).
3. For each module, run `tofu apply -refresh-only -auto-approve -input=false`. A refresh-only apply writes state, which re-encrypts it with P2. If a module has no changes and OpenTofu skips the write, force a write via `tofu state push` of the pulled state with a serial bump (verify the exact behavior. 06-AC-6 asserts the outcome, not the mechanism).
4. Verify that each module decrypts with **P2 only** (no fallback).
5. Re-seal the bundle (plan 35): P2 becomes the current `SC-TOFU-ENCRYPTION`, and P1 is kept as instance `previous` in the bundle while any **retained** version of any module is still P1-encrypted. `state verify` lists the versions and tries P2 then P1 on each; once no retained version needs P1 (they expired, or were re-encrypted by `./bootstrap rotate tofu-passphrase --reencrypt-history`, which re-uploads each retained noncurrent version re-encrypted with P2 as a new version and then lets the old ones expire), P1 is dropped from the bundle at the next re-seal (BOOT-25). The newest-100 lifecycle rule therefore cannot pin P1 forever.
6. Run `state verify`.

The step is idempotent: when a module already decrypts with P2 only, it is skipped.

### 20.4 Lost passphrase or lost bucket: rebuild by import

If state can no longer be decrypted or no longer exists:
1. `./bootstrap state import --module compute` runs `OrphanScan` against the provider (plan 03), which lists the resources named `sc-<cluster>-node-*`.
2. It generates `import` blocks and a fresh state with a **new** passphrase, which requires `./bootstrap rotate refresh-bundle`.
3. `tofu plan` must show imports only, plus no-op.
4. The operator confirms, and sc-bootstrap applies.

The storage module is reconstructed the same way by importing the existing buckets. Recovery uses no cluster component (SPEC §15). The RTO is bounded by provider API latency, typically < 30 min, inside the 2 h target.

### 20.4a Moving state to a new object-storage backend (`./bootstrap state migrate-backend`; `replace-object-storage.md`, DR-13)

After `./bootstrap storage apply --migrate` created the new buckets: for each existing module, read the current version from the old backend (old credentials from the bundle), decrypt it, write it to the same key in the new `tofu-state` bucket with the new `tofu-state` credential (OpenTofu `init -migrate-state` from an old-backend override to the new backend), verify that the address set and lineage are unchanged and that `tofu plan` shows 0 changes, and record the old backend in the journal. Old state history stays in the old bucket (never deleted by sc-bootstrap). If the old state is unreadable, use §20.4.

### 20.5 Black start (plan 45)

The `recover` pipeline's `state-recover` phase needs only: a GitHub clone, the toolbox, `bootstrap.env` (S3 and provider credentials) and the bundle plus passphrase. It runs `InitRemote` for each module, then `Verify` and a provider inventory comparison (plan 50 §14.9).

## 21. Observability

- Off-cluster: `state status` output, conformance and verify JSON in run directories and S3, and V-33 in the bootstrap report.
- **In-cluster signal without secrets (ADR-0100, ADR-0553).** Two check CronJobs in `dr-tests` (plan 44 framework; they exit 0 iff the invariant holds and kube-state-metrics turns failure or staleness into alerts):
  - `restore-test-tofu-state` (daily, `0 5 * * *`, plan 44 RT-5, test id `rt-tofu-state`): with the `tofu-state-ro` credential, reads the newest `restore-tests/*.json` written by `./bootstrap state verify` and checks `schema-valid`, `outcome-passed` and `fresh` (≤ 35 days). Failure or staleness → **`SCTofuStateRestoreTestFailed`** (catalogue; replaces the former `TofuStateRestoreTestFailed`/`…Overdue`).

  - Bucket versioning of `<prefix>-tofu-state` is checked by plan 14's `objstore-audit` → **`SCObjectStorageConfigDrift`** (replaces `TofuStateVersioningDisabled`).

## 22. Testing strategy

- **Unit:** backend and encryption rendering (golden files; the passphrase never appears in rendered files, only in env); conformance logic against an in-memory S3 fake configurable to ignore `If-None-Match`, return 409, or lack versioning; the version-selection algorithm for restore.
- **Integration** (`make test-integration`, SeaweedFS `s3-emulator` per ADR-0205/CD-12; its conditional-write support is asserted by plan 14's `make test-s3-emulator`): full storage apply → conformance → migrate → compute init → lock contention (two `tofu plan` processes; the second fails with a lock error) → rotation (P1→P2 with fallback, then P2 only) → restore of a previous version → import rebuild with fake provider resources.
- **Negative integration:** an `s3-emulator` proxy fixture that strips `If-None-Match` makes conformance fail C2 with `PF_S3_LOCK_UNSUPPORTED`, and no state is written remotely.
- **Real provider (P01):** the same suite against the operator's actual S3 provider (OVH Object Storage for the reference install), run once by `./bootstrap` itself and by `make e2e-s3-conformance S3_ENV=…` (opt-in).

## 24. Explicit non-goals

- State in the cluster (Kubernetes backend), Terraform Cloud or HTTP backends.
- DynamoDB-style lock tables. Native S3 lockfiles only.
- Cloud KMS key providers. They would add a black-start dependency (ADR-0012 rationale).
- Automatic deletion or compaction of state history.
