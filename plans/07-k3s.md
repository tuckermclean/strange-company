# 07 — k3s

**Status:** Stage-0 plan (draft)
**DAG nodes:** F10 (co-owned with 08), P03 (co-owned with 08, 09), H01 (co-owned with 47)
**Related plans:** [03](03-provider-interface.md) (normalized nodes), [08](08-node-security.md) (baseline, firewall), [09](09-networking.md) (CNI, CoreDNS), [10](10-tls-certificates.md), [14](14-object-storage.md) (bucket `etcd-snapshots`), [35](35-secrets.md), [45](45-recovery.md), [47](47-ha-expansion.md), [48](48-upgrade.md), [50](50-bootstrap-orchestrator.md) (configure phase), [51](51-capacity-and-scheduling.md) (reserved/eviction numbers)
**Contracts:** consumes `provider.schema.yaml` (node addresses), `bootstrap-config.schema.yaml`; produces no new contract (k3s config is rendered, not a cross-component API)
**ADRs:** relies on ADR-0010, ADR-0011, ADR-0012, ADR-0020; introduces ADR-0154 (k3s lifecycle via Ansible, split config) and ADR-0158 (etcd restore versus rebuild)

## 1. Purpose

Define how k3s is installed, configured, kept consistent, snapshotted, recovered and grown from one embedded-etcd server to a three-member quorum. This plan owns the k3s server configuration, the etcd lifecycle (snapshots, off-node copies, member management, restore), the k3s token, k3s-internal certificates, kubelet resource-protection flags (the numbers come from plan 51), API-server audit logging and the version-selection rule.

## 2. Requirements derived from SPEC.md

1. The Kubernetes distribution is k3s. [SPEC §16, §20]
2. The first node uses embedded etcd from the start: one node is server, control plane, etcd member and worker. [SPEC §16, §11]
3. Expansion goes 1 etcd member → node 2 → node 3 → a three-member quorum, without rebuilding. [SPEC §16, §12, §119 PHASE 6]
4. Critical k3s server configuration remains consistent across control-plane nodes. [SPEC §16]
5. Network-policy enforcement stays enabled. Inter-node pod traffic is encrypted with flannel WireGuard. [SPEC §18; ADR-0011]
6. etcd snapshots are retained and important snapshots are copied off-node. [SPEC §110, §29]
7. Stage 0 defines when to restore etcd versus rebuild from source. [SPEC §110]
8. The k3s token is a secret class with creator, consumer, storage, rotation and recovery. [SPEC §99]
9. Infrastructure has scheduling priority over agents, so a worker must not OOM-kill etcd. [SPEC §89]
10. Root disks must not fill because cleanup policy was omitted (logs, images, snapshots). [SPEC §107]
11. Infrastructure control interfaces are not exposed publicly. [SPEC §18]
12. Procedures exist for lost etcd member and etcd restore. [SPEC §113]

Derived requirements:

- **07-R-1** k3s is installed by the Ansible role `k3s` from a checksum-verified binary pinned in `versions/k3s.lock.yaml`. The upstream `install.sh` is not used and nothing is piped from curl to a shell (ADR-0154).
- **07-R-2** Configuration is split into a *cluster file*, byte-identical on all servers, and a *node file* (§9.1). The cluster file's SHA-256 is equal on every server at all times outside an in-progress `./bootstrap` run.
- **07-R-3** Bundled Traefik and ServiceLB are disabled (ADR-0010). Bundled CoreDNS is replaced by a Strange Company–rendered manifest (ADR-0153, plan 09). local-path-provisioner and metrics-server stay enabled.
- **07-R-4** Secrets are encrypted at rest (`secrets-encryption: true`).
- **07-R-5** Scheduled etcd snapshots run every 6 hours. 28 are retained locally, and every snapshot is copied to `s3://<prefix>-etcd-snapshots/<install-id>/`. An on-demand snapshot named `pre-<operation>-<UTC timestamp>` is taken before every k3s upgrade, server join, server removal, etcd restore and Longhorn or CNPG major upgrade.
- **07-R-6** Port 6443 is reachable only from peer nodes, the pod network and loopback. Operators reach it through an SSH local forward (plan 50 §14.4).
- **07-R-7** The k3s process (kubelet, apiserver, etcd and containerd supervision) is outside the `kubepods` cgroup and is protected by `kube-reserved`/`system-reserved` accounting and `enforce-node-allocatable=pods`.
- **07-R-8** kube-apiserver audit logging is enabled at Metadata level, never logs request or response bodies for Secrets, and is bounded to ≤ 300 MiB on disk.
- **07-R-9** Server count is always 1 or 3 (later 5) in steady state. A two-member etcd exists only transiently during expansion or replacement (§14.3).

## 4. Outputs

- A running k3s server on every server node, with systemd unit `k3s.service`.
- `/etc/rancher/k3s/config.yaml` (cluster file, mode 0600, root), `/etc/rancher/k3s/config.yaml.d/10-node.yaml` (node file, 0600), `/etc/rancher/k3s/audit-policy.yaml` (0600), `/etc/rancher/k3s/psa.yaml` (0600; the PodSecurity `AdmissionConfiguration` copied verbatim from plan 37 §9.3, identical on every server).
- The node-local admin kubeconfig `/etc/rancher/k3s/k3s.yaml` (0600, `system:admin`, group `system:masters`). It **never leaves the node** (AUTH-7): it is the cluster break-glass identity (used only as `ssh sc-breakglass@<node> sudo k3s kubectl …`, plan 15) and nothing else uses it routinely.
- `/etc/rancher/k3s/registries.yaml` (0600, identical on every server): `configs."git.<baseDomain>".tls.ca_file: /etc/sc/trust/git-registry-ca.crt`, a bundle of the system roots **plus** the `sc-internal-ca` root (`config/internal-ca.crt`, plan 10). Node-side pulls from the Forgejo registry therefore succeed whether `public-wildcard` is ACME-issued or, during a rate-limited black start, temporarily issued by `sc-internal-ca` (blind review DR-B10; whether containerd's `ca_file` replaces or extends the system pool is verified on baseline k3s v1.36.x / containerd v2.3, 07-AC-27, which is why the bundle contains both).
- Operator and automation identities, distinct from `system:admin` (AUTH-7):
  - ClusterRoleBinding **`sc-cluster-admins`** (subject group `${k3s_operator_group}` → `cluster-admin`), shipped by the `k3s` role as a k3s auto-deploy manifest `/var/lib/rancher/k3s/server/manifests/sc-cluster-admins.yaml` (identical on every server; applied by k3s's deploy controller before Flux exists; plan 50 relies on the name). `k3s_operator_group` defaults to `sc:cluster-admins` (`group_vars/all/k3s.yaml`); emergency revocation of every operator and automation certificate sets it to `sc:cluster-admins-g2` (then `-g3`, …) and runs `./bootstrap configure --tags k3s`, after which new certificates are issued with the new group.
  - Operator certificate: `sc-bootstrap kubeconfig refresh` (plan 50) creates a key and CSR in the toolbox tmpfs (`/run/sc/secrets/kube/`), and over SSH as `sc-admin` signs it **without any API call** with `sudo openssl x509 -req -CA /var/lib/rancher/k3s/server/tls/client-ca.crt -CAkey …/client-ca.key -days 30` (subject `CN=sc-operator:<operator>`, `O=${k3s_operator_group}`). The resulting kubeconfig (server `https://127.0.0.1:16443`) is `SC-K3S-ADMIN-KUBECONFIG` (register name; plan 50's `SC-BOOTSTRAP-KUBECONFIG` is renamed). It expires after 30 days and is refreshed on every `./bootstrap` run that needs the API.
  - Ansible identity on nodes: the `k3s` role signs `CN=sc-ansible:<node>`, `O=${k3s_operator_group}` the same way into `/etc/rancher/k3s/sc-ansible.kubeconfig` (0600) on every configure run; every node-side `kubectl` call of the roles uses it, never `k3s.yaml`.
- etcd snapshots locally (`/var/lib/rancher/k3s/server/db/snapshots/`) and in S3. k3s also records them as `ETCDSnapshotFile` objects (`etcdsnapshotfiles.k3s.cattle.io`, verify).
- Node-exporter textfile metrics written by `sc-node-facts.timer` (§21): `sc_k3s_cluster_config_info{sha256}`, `sc_k3s_version_info{version}`, `sc_k3s_cert_expiry_timestamp_seconds{cert}`, `sc_etcd_snapshot_last_success_timestamp_seconds{location}`, `sc_k3s_audit_breakglass_requests_total` (count of audit events with `user.username == "system:admin"` whose `userAgent` does not start with `k3s/`; AUTH-7. Whether k3s internal controllers ever act as `system:admin` is verified by 07-AC-26, and the filter is adjusted once if they do).
- `/usr/local/bin/etcdctl` (pinned) and the wrapper `/usr/local/sbin/sc-etcdctl`, which presets endpoints and client certificates under `/var/lib/rancher/k3s/server/tls/etcd/`.
- The node label `strange.company/node-role=server` on servers.

## 8. Internal interfaces

- Ansible role `k3s` (under `infra/ansible/roles/k3s/`). Task files: `install.yml` (download, verify, place binary, unit), `config.yml` (render cluster and node files, audit policy), `start-init.yml` (node-01 with `cluster-init`), `join.yml` (servers joining via `server:`), `facts.yml` (`sc-node-facts` timer), `etcdctl.yml`, `verify.yml` (post-start assertions), `upgrade.yml` (plan 48).
- Ansible role `k3s` reads the full join token from node-01 (`/var/lib/rancher/k3s/server/token`, format `K10<ca-sha256>::server:<secret>`) and uses it in joiners' node files. That pins the cluster CA, so a joiner cannot be MITM'd.
- `sc-node-facts` is a systemd timer (every 5 min) delivered by plan 08's baseline role but populated with k3s facts by this role. It writes the textfile metrics atomically (temp file + rename).

## 9. Configuration

### 9.1 Configuration files

**Cluster file `/etc/rancher/k3s/config.yaml`.** It is rendered once from cluster-wide variables and must be byte-identical on every server. Keys (values shown for defaults):

```yaml
# rendered by infra/ansible/roles/k3s/templates/config.yaml.j2 — do not edit
token: "<SC-K3S-TOKEN server secret>"
disable: [traefik, servicelb]
flannel-backend: wireguard-native
flannel-external-ip: true            # nodes reach each other on public IPs (ADR-0011)
cluster-cidr: 10.42.0.0/16
service-cidr: 10.43.0.0/16
cluster-dns: 10.43.0.10
cluster-domain: cluster.local
secrets-encryption: true
protect-kernel-defaults: true
prefer-bundled-bin: true             # same iptables/ipset binaries on Debian and Ubuntu
write-kubeconfig-mode: "0600"
etcd-expose-metrics: true
etcd-snapshot-schedule-cron: "0 */6 * * *"
etcd-snapshot-retention: 28
etcd-snapshot-compress: true
etcd-s3: true
etcd-s3-endpoint: "<host[:port] of S3 endpoint>"
etcd-s3-region: "<region>"
etcd-s3-bucket: "<prefix>-etcd-snapshots"
etcd-s3-folder: "<install-id>"
etcd-s3-access-key: "<etcd-snapshots credential id>"
etcd-s3-secret-key: "<etcd-snapshots credential secret>"
default-local-storage-path: /var/lib/strange-company/local-path
tls-san: ["kubernetes", "127.0.0.1", "<every server internal_ip>", "<every server external_ip>"]
kube-apiserver-arg:
  - audit-policy-file=/etc/rancher/k3s/audit-policy.yaml
  - audit-log-path=/var/lib/rancher/k3s/server/logs/audit.log
  - audit-log-format=json
  - audit-log-maxsize=50          # MiB
  - audit-log-maxbackup=5
  - audit-log-maxage=7            # days
  - admission-control-config-file=/etc/rancher/k3s/psa.yaml   # PSA defaults: restricted unless labeled (plan 37 §9.3); k3s's own `pod-security-admission-config-file` key MAY be used instead if the pinned k3s documents it (verify, 07-AC-24)
kube-controller-manager-arg:
  - terminated-pod-gc-threshold=500
  - use-service-account-credentials=true   # per-controller identities, e.g. Job-created pods are created by system:serviceaccount:kube-system:job-controller (plan 37 VAP params; verify, 07-AC-25)
kubelet-arg:
  - system-reserved=cpu=250m,memory=512Mi,ephemeral-storage=<computed>
  - kube-reserved=cpu=500m,memory=1024Mi
  - enforce-node-allocatable=pods
  - eviction-hard=memory.available<300Mi,nodefs.available<10%,nodefs.inodesFree<5%,imagefs.available<10%
  - eviction-soft=memory.available<600Mi,nodefs.available<15%
  - eviction-soft-grace-period=memory.available=90s,nodefs.available=2m
  - eviction-max-pod-grace-period=60
  - eviction-minimum-reclaim=memory.available=200Mi,nodefs.available=2Gi
  - image-gc-high-threshold=80
  - image-gc-low-threshold=70
  - container-log-max-size=10Mi
  - container-log-max-files=3
  - shutdown-grace-period=90s
  - shutdown-grace-period-critical-pods=30s
```

Notes:
- `tls-san` lists every server's addresses, which changes when servers are added. During expansion (plan 47) the new cluster file is rendered with the final server set and rolled to all servers *before* the joins, so it stays identical. Changing `tls-san` makes k3s regenerate the serving certificate at restart (verify, 07-AC-21).
- On `constrained` nodes (MemTotal < 11 GiB) the memory reservations are `system-reserved memory=448Mi` and `kube-reserved memory=896Mi` (plan 51 §9.2). A cluster cannot mix node size classes in its cluster file. Plan 03 already requires equal node shapes per profile; if a heterogeneous `existing` cluster is detected, configure fails with `K3S_MIXED_SIZE_CLASS` (open question Q-07-04).
- `ephemeral-storage=<computed>` = `fsSize(/var/lib) − floor(0.20 × fsSize)`, rounded down to whole GiB, so allocatable ephemeral storage is about 20% of the root filesystem (plan 51 §11). This value depends on disk size, so it is the one numeric field that could differ between servers. Plan 03 requires equal disk sizes within a profile. If sizes differ, Ansible uses the **minimum** across servers so the file stays identical.
- Not set, deliberately: `disable-network-policy` (it must stay enabled, ADR-0011); `cluster-init` and `server` (node file only); `node-taint` (servers are also workers); `embedded-registry` (no Spegel); `secrets-encryption-provider` (default `aescbc`; `secretbox` MAY be adopted after verification, Q-07-02).

**Node file `/etc/rancher/k3s/config.yaml.d/10-node.yaml`** (per node). k3s merges `config.yaml.d/*.yaml` drop-ins after `config.yaml` (verify, 07-AC-3):

```yaml
node-name: node-02
node-ip: 203.0.113.11            # addresses.internal_ip
node-external-ip: 203.0.113.11   # addresses.external_ip, or internal_ip when external_ip is null
node-label: ["strange.company/node-role=server"]
```

`cluster-init: true` stays in node-01's node file after initialization. k3s ignores it once etcd data exists (verify, 07-AC-4). It must never be set on a joiner.

## 10. Secrets

| Secret class | Role here | Notes |
|---|---|---|
| `SC-K3S-TOKEN` | Consumed. The *server* value is in the cluster file. An optional *agent* value (`agent-token`) exists only if agent-only nodes are ever added (§24) | **Creator:** plan 50 secret generation (32 random bytes, hex). **Storage:** recovery bundle (authoritative at run time) + SOPS `secrets/offcluster/<cluster>/k3s-token.sops.yaml`, encrypted to the **recovery recipient only** so the in-cluster age key cannot read it (plan 01 OQ-01-2, ADR-0101). Decrypted only into the toolbox tmpfs `/run/sc` during a run. **Consumers:** Ansible `k3s` role; k3s uses it to encrypt bootstrap data (CA keys, encryption config) inside etcd and in snapshots. **Rotation:** `k3s token rotate --new-token <new>` on one server (k3s ≥ 1.28, verify), then re-render the cluster file on every server and restart them one at a time. Snapshots taken before rotation need the **old** token to restore, so the old value is kept in the recovery bundle for 30 days (snapshot retention) under `k3s_token_previous`. **Recovery:** from the bundle, or from the SOPS copy with the offline recovery identity. Without it, etcd snapshots are unrestorable and the only path is rebuild-from-Git (§20.2). |
| `SC-OBJECT-STORAGE` purpose `etcd-snapshots` | Consumed (cluster file) | Needs `PutObject`, `GetObject`, `ListBucket` and `DeleteObject`, because k3s prunes S3 snapshots beyond retention. Bucket versioning plus a noncurrent-version lifecycle of ≥ 30 days (plan 14) makes pruning recoverable |
| `SC-K3S-ADMIN-KUBECONFIG` (plan 35 register; plan 50 called it `SC-BOOTSTRAP-KUBECONFIG`) | Produced: per-operator 30-day client certificate signed by the k3s client CA (§4, AUTH-7) | Not `k3s.yaml`. Revocation: change `k3s_operator_group` and run `./bootstrap configure --tags k3s` (the `sc-cluster-admins` binding then names only the new group). Plan 35 updates the register entry |
| `SC-BREAK-GLASS-CLUSTER` (plan 15/35) | Interface | Per ADR-0251 the cluster break-glass path is SSH as node user `sc-breakglass` (plan 08) followed by `sudo k3s kubectl` with the node-local `system:admin` kubeconfig. This plan guarantees that only that path uses `system:admin`, so the audit counter detects it (`SCK3sBreakGlassAuditSeen`; CD-01) |

No new secret class is introduced by this plan.

## 11. Storage

| Path | Contents | Budget (plan 51 §11) |
|---|---|---|
| `/var/lib/rancher/k3s/server/db/etcd` | etcd member data. `quota-backend-bytes` k3s default 2 GiB; WAL | 3 GiB |
| `/var/lib/rancher/k3s/server/db/snapshots` | 28 compressed snapshots, typically 5–40 MiB each at this scale | 2 GiB |
| `/var/lib/rancher/k3s/server/logs` | audit log ≤ 6 × 50 MiB | 0.5 GiB |
| `/var/lib/rancher/k3s/agent/containerd` | images and container layers (plan 51 image budget) | 15–20 GiB |
| `/var/log/pods` | container logs, 10 MiB × 3 per container | ≤ 3 GiB |

etcd needs low fsync latency. Preflight (plan 08 §14.2) measures the 99th percentile fdatasync latency on `/var/lib/rancher` with `fio` and requires ≤ 10 ms, failing configure with `NODE_DISK_TOO_SLOW` above 25 ms (warn between 10 and 25 ms). At runtime `SCEtcdSlowDisk` (plan 42) alerts at p99 WAL fsync > 500 ms.

## 12. Resource requirements

The k3s server process (apiserver, controller-manager, scheduler, embedded etcd, kubelet, flannel, kube-router netpol controller, containerd supervision) has these budgets:

| Profile | Expected working set (RSS) | Reserved accounting | CPU |
|---|---|---|---|
| self-hosting-minimum (12 GiB) | 0.8–1.1 GiB | `kube-reserved memory=1024Mi` + `system-reserved memory=512Mi` (OS, sshd, journald, chrony, iscsid) | `kube-reserved cpu=500m`, `system-reserved cpu=250m` |
| 8 GiB constrained | 0.7–1.0 GiB | 896Mi + 448Mi | same |
| small-ha per server | 0.9–1.3 GiB (three-member etcd adds peer traffic) | same as the node class | same |

The P12 memory gate (plan 51 §14) validates the reservations: measured `(MemTotal − MemAvailable) − Σ pod working set` must be ≤ system-reserved + kube-reserved. If it is not, the reservation is raised by PR and the gate is re-run.

## 13. Security boundary

- **Trust:** the k3s server is the highest-trust component on the node (root, holds CA keys).
- **Reachable from:**
  - 6443: peers, the pod CIDR and loopback (SSH forward).
  - 2379/2380: peer servers only.
  - 2381 (etcd metrics, plaintext HTTP): peers and the pod CIDR.
  - 10250 (kubelet): peers and the pod CIDR.
  - 51820/udp: peers.
  - Enforcement is the plan 08 nftables table.
  - Residual risk: metrics on 2381 cross the public network unencrypted between nodes at small-ha (low sensitivity; recorded in plan 08 §13).
- **etcd peer and client traffic** uses k3s-managed mutual TLS. The firewall is defense in depth.
- **Secrets at rest:** `secrets-encryption: true`. Snapshots contain encrypted Secrets plus bootstrap data encrypted with the token, so a stolen snapshot without the token exposes no Secret values (verify, 07-AC-12).
- **Files:**
  - `/etc/rancher/k3s/*` and `/var/lib/rancher/k3s/server` are root-only (0600/0700).
  - The admin kubeconfig `k3s.yaml` never leaves the node (AUTH-7); operators hold only their own 30-day `sc-operator:<name>` certificate (§4).
- **API hardening (CIS-aligned, practical):**
  - anonymous auth is disabled (k3s default, verified by 07-AC-14);
  - `protect-kernel-defaults`;
  - audit logging;
  - secrets encryption;
  - PSA and VAP (plan 37);
  - `profile` mode is not used.
  - Items deliberately not applied: `--profile=cis` (it would force `protect-kernel-defaults`, PSA config and NetworkPolicies that conflict with plan 36/37 ownership). The equivalent controls are applied individually.

## 14. Happy path

### 14.1 Install (configure phase, single node)

1. Plan 08 roles complete: packages, sysctls, modules, firewall (peer set = {node-01}), chrony synced.
2. `install.yml`: download `k3s` from the GitHub release URL in the lock, verify sha256, install to `/usr/local/bin/k3s` (0755), and create symlinks `kubectl`, `crictl` and `ctr` in `/usr/local/bin`. Template `k3s.service` (Type=notify, `ExecStart=/usr/local/bin/k3s server`, `KillMode=process`, `Delegate=yes`, `LimitNOFILE=1048576`, `TasksMax=infinity`, `TimeoutStartSec=0`, `Restart=always`, `RestartSec=5s`), plus `k3s-killall.sh` from the pinned k3s source tag (checksummed).
3. `config.yml`: render the cluster file, node file (with `cluster-init: true`), audit policy and `psa.yaml` (plan 37 §9.3), and the CoreDNS `.skip` and manifest from plan 09 into `/var/lib/rancher/k3s/server/manifests/`.
4. `start-init.yml`: `systemctl enable --now k3s`. Wait ≤ 300 s for `/readyz` on 127.0.0.1:6443 and for `kubectl get node node-01` Ready.
5. `verify.yml` assertions (each a deterministic command; failures abort with a named error):
   - `kubectl get --raw /readyz` returns `ok`;
   - `sc-etcdctl endpoint health` reports `healthy` for one endpoint;
   - `sc-etcdctl member list` shows 1 member;
   - `ip -d link show flannel-wg` shows `wireguard`;
   - `kubectl -n kube-system get deploy traefik` returns NotFound;
   - no `svclb-*` DaemonSet exists;
   - `k3s secrets-encrypt status` reports `Encryption Status: Enabled`;
   - `k3s etcd-snapshot save --name pre-configure-verify` succeeds, and a matching object appears in S3 within 120 s.
6. Write `sc-node-facts` metrics. Plan 50 runs `sc-bootstrap kubeconfig refresh` to obtain the operator certificate (§4).

### 14.2 Re-run (idempotent converge)

Re-running `site.yml` with unchanged inputs reports `changed=0` (plan 50 configure done check). A changed cluster file triggers a **rolling** restart: one server at a time. The next server restarts only after the previous one is Ready and `sc-etcdctl endpoint health --cluster` is all healthy (timeout 300 s per server).

### 14.3 Join servers (H01, sequenced by plan 47)

1. Re-render the cluster file with the final `tls-san` list (all 3 servers). Firewall peer sets now contain all 3 nodes on **all** nodes (plan 08). Roll the cluster file to node-01 (restart) and verify.
2. `k3s etcd-snapshot save --name pre-join` on node-01 and confirm the S3 copy.
3. Join node-02: install the binary, render the cluster file (identical) and a node file with `server: https://<node-01 internal_ip>:6443` and the full token, then start. Wait ≤ 600 s for: node Ready; `sc-etcdctl member list` shows 2 members, both `started`, `isLearner=false`; endpoint health all healthy.
4. **Immediately** join node-03 the same way. Wait for 3 started voting members.
5. Record the time between step 3 start and step 4 completion as `etcd_two_member_window_seconds` in the expand journal (target ≤ 1200 s).
6. Verify the cluster file hash is equal on all three servers.

Quorum risk analysis (members → quorum → failures tolerated):

| Voting members | Quorum | Failures tolerated | Note |
|---|---|---|---|
| 1 | 1 | 0 | self-hosting-minimum steady state |
| 2 | 2 | 0 | **worse than 1**: the loss of either member stops writes. Transient only |
| 3 | 2 | 1 | small-ha steady state |
| 4 | 3 | 1 | never used |
| 5 | 3 | 2 | future option |

k3s is expected to add new members as etcd **learners** and promote them once caught up (k3s ≥ 1.27, verify, 07-AC-20). Learners do not count toward quorum. If that holds, a joiner that dies before promotion does not break quorum. If verification shows k3s adds voting members directly, the risk window is the time between `member add` and the joiner's etcd start. Mitigations: the pre-join snapshot; both new nodes are provisioned, baseline-configured and firewall-open *before* step 3; and the abort path in §15 (`cluster-reset` on node-01).

## 15. Failure modes

| Failure | Detection | Effect | Automated response | Procedure |
|---|---|---|---|---|
| Binary checksum mismatch | `install.yml` sha256 check | install aborts | none (fail closed, `K3S_CHECKSUM_MISMATCH`) | fix lock file via PR |
| k3s fails to start (config error) | systemd `failed`, `/readyz` timeout | node unusable | Ansible prints `journalctl -u k3s -n 200`; run marked failed | `bootstrap-resume.md` (plan 50) |
| Cluster file drift between servers | `SCK3sServerConfigDrift` (count distinct `sc_k3s_cluster_config_info` sha256 > 1 for 15m) | k3s may refuse joins ("critical configuration value mismatch") or behave differently per server | none | re-run `./bootstrap configure` |
| k3s version differs from lock | `SCK3sVersionDrift` (`count(count by (version)(sc_k3s_version_info)) > 1` for 2h, or ≠ `sc_k3s_expected_version_info`) | skew | none | `upgrade-k3s.md` |
| Single etcd member corrupt/lost on a 1-node cluster | `SCEtcdNoLeader`, apiserver down | total control-plane outage; workloads keep running until restart | none | `restore-etcd.md` |
| One member down in 3-member cluster | `SCEtcdMemberMissing` | no write impact; no fault tolerance left | none | `lost-etcd-member.md` / `lost-node.md` |
| Quorum lost (2 of 3 down) | `SCEtcdNoLeader` | API read-only/unavailable | none | `restore-etcd.md` §B (cluster-reset on survivor) |

| Token lost | discovered at restore | snapshots unrestorable | none | rebuild path (§20.2, plan 45) |

## 16. Retry behavior

- Ansible download: 3 attempts, 10 s backoff. Service start wait: 300 s (init) / 600 s (join), no automatic retry. A failed join is never retried automatically; the expand journal stops and requires the operator (the quorum risk makes blind retries unsafe).
- Rolling restarts stop at the first server that does not become healthy within 300 s.
- etcd-s3 upload failures are retried by k3s on the next schedule. There is no extra retry loop. The alert covers persistence.

## 17. Idempotency behavior

- Binary placement is keyed by sha256: same hash means no change.
- Config rendering is template-based. An unchanged render means no restart; a changed render means a rolling restart (§14.2).
- `cluster-init` on an already-initialized node is a no-op (verify).
- `join.yml` on a node already in `member list` with matching name and peer URL is a no-op. If the node is in `member list` but its local `db/` is empty (stale member), the task fails with `K3S_STALE_MEMBER` and points to `lost-etcd-member.md`. It does not auto-remove members.
- `k3s etcd-snapshot save --name X` creates a new uniquely timestamped snapshot each time. Harmless.

## 18. Bootstrap behavior

- **configure phase** (plan 50 §14.4): runs §14.1 on node-01 only. The done check includes Ansible `--check` = `changed=0` and `kubectl get nodes` = expected count Ready with the lock version.
- **Black start** (plan 45): the same role installs a fresh cluster with a **new** etcd (rebuild path). It reuses `SC-K3S-TOKEN` from the bundle, so pre-loss snapshots remain decryptable if a later targeted restore is chosen. k3s generates new server CA material unless restoring from a snapshot.
- Nothing in seed or later phases changes k3s configuration. Post-transfer changes go through Git + `./bootstrap configure` (plan 48).

## 19. Upgrade behavior

### 19.1 Version baseline

**Baseline: k3s v1.36.5+k3s1, line 1.36.x** (`plans/compatibility-baseline.yaml`, CD-29/ADR-0022; embedded etcd v3.6.14, containerd v2.3.4, flannel v0.28.4, CoreDNS v1.14.7, local-path-provisioner v0.0.37, metrics-server v0.9.0). Patches within 1.36.x are Renovate PRs; a new minor (1.37+) is a plan-amendment task that re-checks the criteria below and re-runs every version-sensitive AC. The criteria that selected 1.36 (and will select the next minor):
- (a) the minor has been GA in k3s for ≥ 30 days;
- (b) the support matrices of the pinned Longhorn, CNPG, cert-manager, Traefik, Flux and kube-prometheus-stack versions include that Kubernetes minor (`versions/compat.yaml`, checked by CI node F11, plan 48);
- (c) it is ≥ 1.30 (ValidatingAdmissionPolicy GA, ADR-0014).

Patch releases within the pinned minor are adopted through Renovate PRs (plan 48). **Version-sensitive flags re-checked against 1.36:** cgroup v1 is unsupported by the 1.36 kubelet (plan 08 already requires cgroup v2); the kubelet flags in §9.1 (`system-reserved`, `eviction-*`, `image-gc-*`, `container-log-*`, `shutdown-grace-period*`, `enforce-node-allocatable`) are deprecated CLI forms that 1.36 still accepts, verified by 07-AC-28; if a future minor removes them, the role switches to a `KubeletConfiguration` file passed as `kubelet-arg: config=…` with the same values. Architecture: amd64 only for MVP. arm64 binaries MAY be added to the lock later.

### 19.2 Upgrade mechanics

Owned by plan 48 and `procedures/upgrade-k3s.md`: Ansible-driven, one minor at a time, server by server, with a pre-upgrade snapshot and health gates. system-upgrade-controller is not used (ADR-0154).

### 19.3 k3s certificate rotation

k3s client and server leaf certificates are valid for 365 days. k3s renews any cert within 90 days of expiry when the service starts (verify, 07-AC-17). CA certificates last 10 years.
- The monthly reboot (plan 08) restarts k3s and therefore renews certs in time. `SCK3sCertificateExpiringSoon` (30 days) catches a node that has not restarted.
- Manual rotation: `k3s certificate rotate` with k3s stopped, then start, one server at a time. Rotation does not touch the client CA, so operator and Ansible certificates stay valid; they are re-signed on their own 30-day cycle.
- `sc-node-facts` reads expiry dates with `openssl x509 -enddate` over `/var/lib/rancher/k3s/server/tls/*.crt` and `/var/lib/rancher/k3s/agent/*.crt`. This avoids depending on `k3s certificate check` output format.

### 19.4 Secrets-encryption key rotation

Annually, and after any suspected node compromise: `k3s secrets-encrypt rotate-keys` on one server (k3s ≥ 1.28, verify), wait for `k3s secrets-encrypt status` to show the reencryption finished on all servers, then do a rolling restart. Take a pre-snapshot first.

## 20. Recovery behavior

### 20.1 Decision tree: etcd restore versus rebuild from Git (ADR-0158)

```text
Is at least one server's etcd data intact and that member able to start?
├─ YES, quorum intact (≥2 of 3, or 1 of 1)          → no restore. Replace missing members (lost-etcd-member.md)
├─ YES, but quorum lost (1 of 3 survivors)            → cluster-reset on the survivor WITHOUT a snapshot
│                                                       (keeps latest data), then rejoin others (restore-etcd.md §B)
└─ NO surviving etcd data
   ├─ Are the nodes' data disks (local-path PGDATA, /var/lib/longhorn) intact,
   │  is SC-K3S-TOKEN available, and is there a snapshot ≤ 24 h old?
   │  ├─ YES → etcd SNAPSHOT RESTORE (restore-etcd.md §A/§C). Rationale: PV/PVC bindings,
   │  │        Longhorn volume CRs and CNPG cluster objects then point at the surviving
   │  │        on-disk data, giving minutes-scale recovery with no data restores.
   │  └─ NO  → REBUILD FROM GIT (plan 45 total-cluster-loss / black start): new etcd, Flux
   │           re-applies desired state, data comes back from CNPG/Longhorn/S3 backups.
   └─ (total loss of all nodes) → always REBUILD. A snapshot restore onto new machines
                                  would resurrect PV objects pointing to disks that no longer
                                  exist and Longhorn/CNPG state that contradicts reality.
```

Additional rules:
- **Logical damage** (objects deleted or corrupted by a bad change) is fixed by Git revert and Flux reconcile, never by etcd restore, *unless* the damage destroyed controller-generated state that Git cannot recreate and the newest pre-damage snapshot is < 6 h old. In that case the operator chooses restore knowing that all API writes since the snapshot are lost (CNPG instance status, Longhorn replica records, Runner Job objects). After such a restore: Flux reconciles forward; the Runner reconciles executions from `sc-pg` (plan 26); Longhorn re-validates replicas (plan 13 notes replica-rebuild risk at 1 replica).
- Always restore the **newest** snapshot that predates the failure, so the API state is as close as possible to the on-disk data.
- A restore needs the token that was current when the snapshot was taken (§10).

### 20.2 Rebuild

Rebuild is plan 45's black start, using this plan's install path (§18).

### 20.3 Lost member

Covered in `procedures/lost-etcd-member.md`. Remove the member while quorum holds, wipe the node's `server/db`, rejoin. Never remove a member while quorum is already lost; use `cluster-reset` instead.

## 24. Explicit non-goals

- Agent-only (non-server) nodes in MVP or small-ha. The design permits them later: `k3s agent` with `agent-token`, node file `server:`, firewall peers, and no etcd ports. Not implemented or gated.
- External datastore (SQL via kine). Excluded by SPEC §16.
- k3s HA with a fixed registration address or load balancer: joiners use a server IP directly. The operator's API access tunnels to any server.
- Spegel/embedded registry, air-gapped install, SELinux (Debian/Ubuntu use AppArmor).
- The CIS `--profile` flag (§13).
