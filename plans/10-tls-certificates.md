## 1. Purpose

Make every certificate in the system explicit: who issues it, who consumes it, how long it lives, how it renews, what alerts before it expires, and how to recover when issuance fails. That includes the public certificate served by Traefik, the internal CA, certificates managed by other systems (k3s, CNPG, operator webhooks, the Cloudflare edge), behavior without Cloudflare, switching between tunnel and direct mode, and rotation of the internal CA. SPEC §23 requires all of this.

## 2. Requirements derived from SPEC.md

1. Certificate lifecycle is explicit. [SPEC §23]
2. Cloudflare Tunnel MAY terminate public TLS in the normal path. [SPEC §23]
3. The architecture defines internal TLS where needed, direct-ingress mode, certificate renewal, behavior without Cloudflare and failure recovery. [SPEC §23]
4. cert-manager is the default Kubernetes certificate automation. [SPEC §23, §20]
5. Certificate failure has an operator procedure. [SPEC §113]
6. Secret classes have creator, consumer, storage, rotation and recovery. [SPEC §99]

Derived requirements:

- **10-R-1** The public certificate is a Let's Encrypt wildcard (`<domain>`, `*.<domain>`) issued by ACME **DNS-01 in both ingress modes**, so switching modes never changes the certificate and cloudflared can verify the origin against public roots (ADR-0152).
- **10-R-2** The internal CA root is generated once per installation in the toolbox, valid 10 years, SOPS-encrypted in Git to both age recipients, and identical after black start (ADR-0152).
- **10-R-3** Every cert-manager `Certificate` is Ready within 15 minutes of creation and renews when one third of its lifetime remains (`renewBeforePercentage: 33`; AUTH-22: Let's Encrypt is shortening default lifetimes from 90 days, and it no longer sends expiry e-mails, so the expiry alerts are the only notice). Alerts fire at 14 days (warning) and 3 days (page); for lifetimes under 45 days the warning fires at 1/4 of the lifetime (plan 42 renders the threshold from `certmanager_certificate_expiration_timestamp_seconds - certmanager_certificate_renewal_timestamp_seconds`).
- **10-R-4** Certificates owned by other systems (k3s, CNPG, Longhorn, operator webhooks, Cloudflare edge) have an expiry signal and a named recovery path.
- **10-R-5** Lab and CI use `letsencrypt-staging` or the internal CA, never production ACME.

## 8. Internal interfaces

### 8.1 Issuers

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata: {name: letsencrypt-prod}
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: ${SC_ACME_EMAIL}
    privateKeySecretRef: {name: acme-account-letsencrypt-prod}
    solvers:
      # exactly one block, selected by SC_ACME_SOLVER (kustomize component per solver)
      - dns01:
          cloudflare:
            apiTokenSecretRef: {name: dns-acme-token, key: api-token}
        selector: {dnsZones: ["${SC_BASE_DOMAIN}"]}
```

`letsencrypt-staging` is identical with `server: https://acme-staging-v02.api.letsencrypt.org/directory` and its own account Secret. Solver variants (kustomize components `gitops/platform/cert-manager-config/components/solver-<name>`):
- `solver-dns01-cloudflare` (default): Cloudflare API token with Zone › DNS › Edit and Zone › Zone › Read on the zone.
- `solver-dns01-rfc2136`: `rfc2136: {nameserver: "${SC_RFC2136_SERVER}", tsigKeyName: "${SC_RFC2136_KEY_NAME}", tsigAlgorithm: HMACSHA256, tsigSecretSecretRef: {name: dns-acme-token, key: tsig-secret}}`.
- `solver-dns01-route53`: `route53: {region: "${SC_ROUTE53_REGION}", hostedZoneID: "${SC_ROUTE53_ZONE}", accessKeyIDSecretRef: {name: dns-acme-token, key: access-key-id}, secretAccessKeySecretRef: {name: dns-acme-token, key: secret-access-key}}`.
- `solver-http01` (direct mode only; F11 rejects it with `INGRESS_MODE=tunnel`): `http01: {ingress: {ingressClassName: traefik}}`. A wildcard cannot be issued by HTTP-01, so the public Certificate switches to per-host SANs (`ingress/public-hosts`).

All three solver credentials are secret class **`SC-DNS-ACME`** (AUTH-13), separate from the toolbox-only `SC-DNS-API`, which carries tunnel-edit and zone-wide record rights and never enters the cluster (35-R-3). Scope of `SC-DNS-ACME`:
- **Preferred (default when the operator can create a second zone):** `_acme-challenge.<domain>` is a CNAME to `_acme-challenge.<challenge-zone>` (a dedicated zone, e.g. `acme-<cluster>.<domain>` delegated or a separate domain), and the token has DNS:Edit on the challenge zone only. cert-manager follows the CNAME (`cnameStrategy: Follow` on the issuer solver; verify on the pinned cert-manager). Compromise of the in-cluster token can then only forge ACME challenges, not production records.
- **Fallback:** a Cloudflare token with Zone › DNS › Edit on the production zone only (no account or tunnel permissions); the residual blast radius (zone records) is recorded in plan 35's register entry.

cert-manager controller flags (HelmRelease values `extraArgs`): `--dns01-recursive-nameservers-only`, `--dns01-recursive-nameservers=1.1.1.1:53,9.9.9.9:53` (plan 09 rewrite safety; also avoids stale negative caching in the cluster resolver), `--enable-certificate-owner-ref=true` (Secrets are garbage-collected with their Certificate), `--max-concurrent-challenges=10`.

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata: {name: sc-internal-ca}
spec:
  ca: {secretName: sc-internal-ca-root}     # Secret in the cluster-resource namespace (cert-manager)
```

### 8.3 Trust distribution

The public root certificate is committed in plaintext at `gitops/clusters/<cluster>/config/internal-ca.crt` (it is not secret). A kustomize `configMapGenerator` in `gitops/platform/cert-manager-config/` emits ConfigMap `sc-internal-ca` (key `ca.crt`, hash suffix disabled so references are stable) into namespaces `monitoring`, `strange-company`, `hermes`, `forgejo`, `woodpecker`. During a CA rotation the file holds both roots (concatenated PEM). No trust-manager is deployed (one fewer controller; the bundle changes only at rotation).

### 8.4 Internal TLS: where it is and is not used

| Path | TLS? | Reason |
|---|---|---|
| Browser → Cloudflare edge → cloudflared → Traefik | yes, verified at each hop | public traffic |
| Browser → Traefik (direct mode) | yes | public traffic |
| In-cluster OIDC client → Traefik (CoreDNS rewrite) | yes, public cert | same names as browsers use |
| Traefik → backend Services | no (HTTP) | stays on the pod network; cross-node pod traffic is WireGuard-encrypted (ADR-0011); same-node interception requires node root, which already defeats TLS key protection |
| API server → admission webhooks | yes | Kubernetes requires it |
| App → PostgreSQL | yes, `sslmode=require` (CNPG certs) | plan 12; `verify-full` is a plan 12 option |
| Hermes → Runner MCP, worker → Runner, worker/Hermes → Gateway, worker → egress-proxy | no in MVP (bearer tokens over HTTP on the pod network) | same reasoning as Traefik → backend; tokens are short-lived and audience-bound. Post-MVP option: `sc-internal-ca` serving certs (open question Q-10-03) |
| Woodpecker agent → server gRPC | no in MVP | same |
| k3s API, kubelet, etcd | yes (k3s-managed mTLS) | plan 07 |

## 13. Security boundary

- `cert-manager` namespace: PSA restricted, tier `platform-critical`. Only cert-manager pods mount `dns-acme-token` and `sc-internal-ca-root`.
- RBAC: no human or automation identity other than cert-manager, Flux (apply) and cluster break-glass can read Secrets in `cert-manager`. The Runner, workers and Hermes have no access (plans 26, 34, 37).
- The DNS provider credential can change every record in the zone (blast radius in the register). It lives only in `cert-manager` and in the toolbox during bootstrap.
- The internal CA has `pathlen:0` and issues only `sc-internal-ca` leaf certs. Its trust is confined to in-cluster clients that mount `sc-internal-ca`; no browser or operator machine is asked to trust it.
- NetworkPolicy (plan 36): cert-manager controller egress to 443 (ACME, DNS APIs) and 53/udp+tcp to `1.1.1.1`/`9.9.9.9`; webhook ingress on 10250 (cert-manager webhook's port, verify) from node IPs and the pod CIDR.

## 14. Happy path

1. **Before seed (plan 50):** `sc-bootstrap secrets gen internal-ca` creates the root if `secrets/cert-manager/sc-internal-ca-root.sops.yaml` does not exist, writes it SOPS-encrypted, writes `config/internal-ca.crt`; stores `SC-DNS-ACME` as SOPS.
2. **Seed layer `cert-manager`:** HelmRelease Ready (webhook answers).
3. **Seed layer `cert-manager-config`:** Secrets decrypted by Flux; ClusterIssuers created. ACME issuers register the account (Ready=True within 2 min). `sc-internal-ca` Ready immediately.
4. `public-wildcard` Certificate issues: DNS-01 TXT record via the provider API, propagation check against public resolvers, finalize. Typical 1–3 min; budget 15 min (10-R-3). Traefik picks up the Secret (plan 09).
5. Steady state: cert-manager renews 30 days before expiry. Each renewal writes a new key (`rotationPolicy: Always`).

## 15. Failure modes

| Failure | Detection | Effect | Automated response | Procedure |
|---|---|---|---|---|
| DNS-01 fails: credential invalid or missing permission | Certificate `Ready=False`, Order/Challenge events `401`/`403`; `SCCertificateNotReady` | new or renewing certs blocked; existing cert valid until expiry | cert-manager exponential backoff (max 32 h between attempts in recent versions, verify) | `certificate-failure.md` §A |
| DNS-01 propagation timeout | Challenge `pending` > 10 min | same | retry | `certificate-failure.md` §A |
| Let's Encrypt rate limit (5 duplicate certificates / week, 50 / registered domain / week) | Order error `rateLimited` | issuance blocked until window passes | backoff | `certificate-failure.md` §B (staging for drills; wait or switch to per-host SANs) |
| ACME directory unreachable | Order errors; egress blocked | same | retry | `certificate-failure.md` §A (NetworkPolicy check) |
| Public cert expired | `SCCertificateExpiryImminent` earlier; at expiry cloudflared returns 502 (origin verification fails) or browsers reject (direct) | public outage | none | `certificate-failure.md` §C |
| Internal CA Secret missing or undecryptable | `ClusterIssuer sc-internal-ca` `Ready=False`; Flux decryption error | new internal certs blocked; prometheus-operator webhook cert cannot renew | none | `certificate-failure.md` §D |
| Internal CA nearing expiry | `SCInternalCAExpiringSoon` | none yet | none | `certificate-failure.md` §E (rotation) |
| cert-manager webhook down | Flux apply errors for Certificates; `up{job="cert-manager"}` | cert objects cannot be changed; existing certs unaffected | restart | `certificate-failure.md` §F |
| k3s certificate near expiry | `SCK3sCertificateExpiringSoon` | API/kubelet TLS failure at expiry | k3s renews at restart | `certificate-failure.md` §K3S |
| CNPG certificate renewal failed | `SCCnpgCertificateExpiringSoon` | DB TLS failure at expiry | CNPG operator retries | `certificate-failure.md` §CNPG |
| Cloudflare edge cert problem | `blackbox-public` `probe_ssl_earliest_cert_expiry` | browser errors | none (Cloudflare-managed) | `certificate-failure.md` §Edge (Cloudflare dashboard; or switch to direct mode) |

## 16. Retry behavior

cert-manager's own backoff for failed Orders and Challenges. Operators force a retry with `./bootstrap exec -- cmctl renew -n ingress public-wildcard` (cmctl ships in the toolbox; plan 02 adds it, verify) after fixing the cause. Never loop `cmctl renew` against production: each successful issuance counts against the duplicate-certificate limit.

## 17. Idempotency behavior

- `sc-bootstrap secrets gen internal-ca` never overwrites an existing root; it only generates when the SOPS file is absent (an explicit `--rotate` flag is needed for §20.4).
- Certificates are declarative; reapplying is a no-op. A changed `dnsNames` list triggers one reissue.
- ACME account registration is idempotent per account Secret.

## 18. Bootstrap behavior

- Seed (P04): §14 steps 2–4. Plan 19 seed gate: `ClusterIssuer Ready=True` for all three issuers; `public-wildcard` `Ready=True` is required for seed-complete condition 5 (public edge check).
- **Black start** (plan 45): the internal CA comes from Git, so internal trust is unchanged. The public certificate is reissued (counts toward the duplicate-certificate limit; drills either use production ACME and count against the limit of 5 duplicate certificates per week, or use `letsencrypt-staging` **together with** the `trust-test-root` component; plan 45 chooses and states which).
- CI fixture clusters (`ci-*`) use `letsencrypt-staging` and a fake DNS zone; k3d tests use `sc-internal-ca` for a fake public cert (no ACME).
- **Test trust root (AUTH-14).** Whenever the public certificate is not publicly trusted (staging or `sc-internal-ca`), the cluster directory enables the kustomize component `gitops/platform/cert-manager-config/components/trust-test-root`. It builds ConfigMap `sc-test-trust` (system roots + the staging root or `config/internal-ca.crt`) in every OIDC-client namespace and patches each client to trust it: Forgejo, platform-probes, Woodpecker, Hermes (`SSL_CERT_FILE=/etc/sc/trust/ca-bundle.crt`, plus `REQUESTS_CA_BUNDLE` for Hermes), and Grafana (`GF_AUTH_GENERIC_OAUTH_TLS_CLIENT_CA`). Production cluster directories never enable it (F11 check `trust-test-root-prod`), and no manifest may set a verification bypass (F11 check `no-tls-skip`: rejects `tls_skip_verify_insecure`, `InsecureSkipVerify`, `SKIP_TLS_VERIFY`, `noTLSVerify`, `insecure-skip-tls-verify`).

## 19. Upgrade behavior

- cert-manager: selection rule "latest cert-manager minor ≥ 14 days old whose supported-Kubernetes list includes the pinned minor" (recorded in `versions/compat.yaml`, plan 48). Upgrades one minor at a time (cert-manager supports skipping, but CRD storage-version migrations are safer serially). Renovate PR → CI (render + k3d install + issue a test cert from a self-signed issuer) → merge → Flux. Remediation class `controller` (rollback on failure).
- CRDs: `crds.enabled: true, keep: true`; deleting the HelmRelease never deletes Certificates.

## 20. Recovery behavior

### 20.1 Public issuance failure

Fix the cause (credential, permission, egress, rate limit), then `cmctl renew`. Existing certificates keep serving until expiry, so a 30-day renewal window is the recovery budget.

### 20.2 Behavior without Cloudflare

- **Cloudflare temporarily down:** tunnel mode loses public access (plan 09 §15). Certificates are unaffected unless DNS-01 renewal falls in the outage window, in which case cert-manager retries later.
- **No Cloudflare at all (install time):** `INGRESS_MODE=direct`, `SC_ACME_SOLVER` ∈ {`dns01-rfc2136`, `dns01-route53`, `http01`}, DNS records managed manually or by the chosen provider (plan 09 §9.4). Everything else is identical.
- **Leaving Cloudflare after install:** switch procedure §20.3 to direct mode, then change the solver by PR (the old wildcard keeps serving during the change).
- **Cloudflare account or DNS zone lost while Cloudflare hosts the zone (AUTH-11b):** `sc-bootstrap dns apply` and the Cloudflare solver are both unusable. Path: (1) create the zone at another DNS provider supported by a solver (rfc2136 or Route 53) and load the records from `./bootstrap exec -- sc-bootstrap dns plan --provider manual`; (2) change the NS delegation at the **domain registrar** (operator-held registrar account; plan 35 to register an operator-offline class); (3) PR switching `INGRESS_MODE=direct` and `SC_ACME_SOLVER` to the new provider; (4) wait for delegation (up to 48 h). The budget is the remaining validity of `public-wildcard` (≥ 1/3 of its lifetime under 10-R-3); renew under the new solver once delegation is visible from 1.1.1.1. Steps are in `edge-ingress-failure.md` §F.

### 20.3 Switching tunnel ↔ direct

Because the certificate is DNS-01-issued in both modes, a switch changes routing only:
1. PR: `cluster-vars.INGRESS_MODE`, (if Authentik is also down and no human can merge in Forgejo, use plan 15's identity-outage change path or plan 55's `emergency-merge.md`; AUTH-6) the ingress component in `clusters/<c>/kustomization.yaml` and `seed/kustomization.yaml` (F11 `ingress-mode-consistency`), regenerated `public-hosts` artifacts.
2. Merge; Flux reconciles Traefik (Deployment ↔ DaemonSet with hostPorts), namespace PSA label, cloudflared present/absent.
3. `./bootstrap exec -- sc-bootstrap dns apply` (CNAME → A records or the reverse). Downtime ≈ DNS TTL (Cloudflare proxied records switch within seconds; DNS-only TTL 60 s set by `dns apply`).
4. Verify plan 09 09-AC-10 and the external port scan (plan 08 08-AC-13).
Switching to `http01` additionally swaps the public Certificate to `public-hosts` (same Secret name).

### 20.4 Internal CA rotation

Triggers: `SCInternalCAExpiringSoon` (365 days left), suspected key compromise, or age-key compromise exposing the SOPS file.
1. `./bootstrap exec -- sc-bootstrap secrets gen internal-ca --rotate` writes root `g<N+1>` to the SOPS file and appends it to `config/internal-ca.crt` (bundle now holds both roots).
2. PR + merge. Flux updates the Secret and the trust ConfigMaps. Consumers that read `ca.crt` reload (or are restarted by a hash annotation).
3. Reissue every `sc-internal-ca` Certificate: `cmctl renew --all -A` filtered by issuer (`kubectl get certificate -A -o json | jq` selection; procedure lists the command).
4. After all are `Ready` with `g<N+1>` issuers (check `openssl x509 -issuer`), a second PR removes `g<N>` from `internal-ca.crt`.
On compromise, step 4 follows immediately after step 3.

## 24. Explicit non-goals

- trust-manager, SPIFFE/SPIRE, service mesh mTLS.
- Cloudflare Origin CA certificates (they are not publicly trusted and would break direct mode).
- A second production ACME CA (ZeroSSL, Google Trust Services). Possible later via PR; it needs an EAB credential, which would be a new secret class.
- Distributing the internal CA to browsers or operator machines.
- Backing up public certificates (reissuable).
