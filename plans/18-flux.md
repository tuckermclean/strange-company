## 1. Purpose

Flux is the normal deployment authority [SPEC §33]. This plan defines:

- the **GitOps tree layout** under `gitops/`;
- the **Flux `Kustomization` graph** and its `dependsOn` order;
- the conventions every `HelmRelease`, `HelmRepository`, `OCIRepository` and `Kustomization` must follow;
- SOPS decryption, prune semantics and prune protection for stateful resources;
- the committed Flux controller manifests (ADR-0016), Flux self-upgrade, suspend/resume, and Flux monitoring and alerts;
- the **offline render/validate gate F11**, which proves the whole tree renders and validates for every cluster and profile before any cluster exists.

Plan 19 uses the same tree to seed from a `Bucket` and then switch to Forgejo. This plan makes sure that switch changes nothing but the source.

## 2. Requirements derived from SPEC.md

1. Flux sources `Forgejo/strange-company` after bootstrap, and that is the normal production path [SPEC §6, §32, §33].
2. Normal production state originates from version-controlled desired state. CI does not deploy production [SPEC §4.2, §33].
3. Seeded resources must be adoptable by Flux without duplicate-resource chaos [SPEC §34]. Seeded releases are represented in normal GitOps state [SPEC §35] (plan 19 verifies; this plan provides the structure).
4. No Bitnami dependencies [SPEC §20].
5. Production images are immutable references, and dependencies are pinned [SPEC §37, §116].
6. Git-resident secrets are SOPS + age encrypted [SPEC §98].
7. Expansion to small-ha does not require a rebuild [SPEC §12]. The one-node system is reduced redundancy, not a separate architecture [SPEC §12].
8. The Flux failure alert exists [SPEC §96], and Flux metrics are collected [SPEC §91] and dashboarded [SPEC §92].
9. Platform dependencies are separately managed GitOps releases. The `strange-company` chart is not an umbrella [SPEC §115].
10. Helm validation and Kubernetes validation run in trusted CI [SPEC §36], deterministically and without paid calls [SPEC §104].
11. **18-R-1:** Every stateful object whose deletion destroys data (Namespaces, PVCs, CNPG `Cluster`, CNPG `ObjectStore`, manually applied CRDs) carries prune protection. F11 fails if one does not (ADR-0304).
12. **18-R-2:** Every layer `Kustomization` is byte-identical between the seed path and the steady path except for the substituted variables `SC_SOURCE_KIND` and `SC_SOURCE_ROOT` (ADR-0300).
13. **18-R-3:** Every chart is pinned: `OCIRepository` by `ref.digest`, and `HelmRepository` charts by exact semver `chart.spec.version` (no ranges). Every rendered container image is digest-pinned.
14. **18-R-4:** Every rendered Namespace is in master plan §5 (with `ci-build` and `monitoring-node`, CD-13), and carries PSA labels (`enforce`, `audit`, `warn`) plus `strange.company/tier` (ADR-0015).
15. **18-R-5:** The Flux controller manifests in Git equal `flux install --export` at the version pinned in `versions/platform.lock.yaml` (ADR-0016).
16. **18-R-6:** Flux holds no write credential to any forge (ADR-0016).

## 6. Owned state

Flux owns no durable data. Its state is (a) Git, which Forgejo owns (system of record), and (b) controller status, artifacts and inventories in etcd and in the source-controller `emptyDir`. All of this can be rebuilt from Git.

- **Writers to `gitops/`:**
  - humans, through PR + CI + human merge (ADR-0019);
  - Renovate, through PR only (plan 23);
  - `sc-bootstrap`, which writes the cluster directory locally before seed and never pushes to a protected branch after control transfer except through a PR (plan 50).
- **No in-cluster component writes Git.**
- **Imperative objects in `flux-system` that are not in Git**, which is the complete list:
  - `Secret/sops-age` (by design, plan 35);
  - `Bucket/flux-system` and `Secret/seed-bucket-credentials` (seed only; deleted at control transfer, plan 19).

## 8. Internal interfaces

### 8.1 Tree layout

```text
gitops/
├── clusters/
│   ├── _template/                    # rendered by sc-bootstrap into clusters/<cluster>/ (plan 50)
│   ├── ci-shm-tunnel/                # committed CI fixture cluster (self-hosting-minimum, tunnel mode)
│   ├── ci-sha-direct/                # committed CI fixture cluster (small-ha, direct mode)
│   ├── ci-handoff/                   # committed fixture used by the k3d handoff test (plan 19)
│   └── <cluster>/                    # one per installation, generated + committed at bootstrap
│       ├── kustomization.yaml        # STEADY root content: flux-system + vars + ../../profiles/<profile> (nothing else; SEED-1)
│       ├── flux-system/
│       │   ├── kustomization.yaml    # gotk-components + gotk-sync + flux-source-auth + patches (§8.7)
│       │   ├── gotk-components.yaml  # `flux install --export` output at pinned version (ADR-0016)
│       │   ├── gotk-sync.yaml        # GitRepository flux-system + root Kustomization flux-system
│       │   └── flux-source-auth.sops.yaml   # Secret flux-system/flux-system (deploy key + known_hosts)
│       ├── seed/
│       │   └── kustomization.yaml    # SEED root content: ../flux-system (root object deleted by patch) + ../vars + ../../../profiles/<profile>/seed
│       ├── vars/
│       │   ├── kustomization.yaml    # lists ONLY cluster-vars.yaml and cluster-secrets.sops.yaml (both in flux-system)
│       │   ├── cluster-vars.yaml     # ConfigMap flux-system/cluster-vars (non-secret variables)
│       │   ├── cluster-secrets.sops.yaml  # Secret flux-system/cluster-secrets (SOPS)
│       │   └── *.sops.yaml           # pre-seed Secrets of other namespaces: delivered by layer `cluster-config`, never by the root
│       ├── cluster-config/
│       │   └── kustomization.yaml    # GENERATED by `sc-gitops gen cluster-config`: every Kubernetes manifest of this cluster dir
│       │                             # outside flux-system/, seed/ and the two root vars files (vars/*.sops.yaml, forgejo/, authentik/,
│       │                             # secrets/<area>/, config/*.yaml ConfigMaps), referenced as ../<path>
│       ├── config/  forgejo/  authentik/  secrets/<area>/   # owning plans' files (plan 01 §6.5); records and manifests may share dirs
│       └── *.yaml records            # bootstrap-config.yaml, inventory.yaml, config/{cluster,forge-init,recovery,…}.yaml: apiVersion
│                                     # strange.company/*, never referenced by any kustomization (F11 `no-records-in-kustomize`)
├── profiles/
│   ├── self-hosting-minimum/
│   │   ├── kustomization.yaml        # resources: [seed, ../../layers/<post-transfer layers>...]
│   │   └── seed/kustomization.yaml   # resources: ../../../layers/<seed layers>...
│   └── small-ha/                     # same shape; adds the small-ha-only layer `kured`
├── layers/                           # one Flux Kustomization object per file (§8.3); profile-agnostic
│   ├── namespaces.yaml  crds.yaml  policies.yaml  cert-manager.yaml  ...
├── components/                       # kustomize Components selected by cluster kustomization
│   ├── ingress-tunnel/               # adds layers/cloudflared.yaml
│   ├── ingress-direct/               # adds direct-mode patches (traefik hostPorts, ACME issuer)
│   └── telemetry-h03/                # adds layers loki, tempo, otel-agent (plan 41 telemetry PR; GC-06)
├── platform/
│   └── <component>/
│       ├── base/                     # HelmRelease, chart source, values ConfigMap generator, extra manifests
│       └── overlays/
│           ├── self-hosting-minimum/
│           ├── small-ha/
│           └── recovery/             # only where plan 45 requires a restore bootstrap (CNPG, Longhorn)
└── apps/                             # project applications (namespace `apps`), one dir per app + kustomization.yaml
```

Rules:
- `gitops/layers/*.yaml` holds **only** `kustomize.toolkit.fluxcd.io/v1` `Kustomization` objects in namespace `flux-system`. No other kind is allowed there (F11 check `layers-only-kustomizations`).
- Each layer's `spec.path` is `${SC_SOURCE_ROOT}/gitops/platform/<component>/overlays/${SC_PROFILE}`, `${SC_SOURCE_ROOT}/gitops/apps` for `apps`, or `${SC_SOURCE_ROOT}/gitops/clusters/${SC_CLUSTER}/cluster-config` for `cluster-config`. Its `spec.sourceRef` is `{kind: ${SC_SOURCE_KIND}, name: flux-system}`. The root `Kustomization` substitutes these three variables (ADR-0300, §8.4).
- Profile selection appears in exactly three places, which must agree (F11 check `profile-consistency`):
  - `clusters/<c>/kustomization.yaml` → `../../profiles/<p>`;
  - `clusters/<c>/seed/kustomization.yaml` → `../../../profiles/<p>/seed`;
  - the root `postBuild.substitute.SC_PROFILE` in `gotk-sync.yaml`.
  Expansion to small-ha (plan 47) is one PR that changes these three lines. `sc-gitops set-profile --cluster <c> --profile small-ha` makes that edit.
- **Cluster-directory delivery (SEED-1).** The root applies only `flux-system/`, the two `flux-system`-namespace objects in `vars/` and the layer Kustomization objects, all of which live in namespaces that exist before the first reconcile. Every other Kubernetes manifest under `gitops/clusters/<c>/` is applied by the seed-set layer **`cluster-config`** (§8.3 row 1c), whose path is `${SC_SOURCE_ROOT}/gitops/clusters/${SC_CLUSTER}/cluster-config` (root-only variable `SC_CLUSTER`, §8.4). It `dependsOn: [namespaces]`, so every target namespace already exists, and `policies` depends on it, so every component layer applies after it. Kustomize cannot glob: `cluster-config/kustomization.yaml` is regenerated by `sc-gitops gen cluster-config --cluster <c>` whenever a phase writes a cluster-dir manifest (plan 50 install-identity, plan 16 forge-init, plan 17 M5, plan 45 recover, `ci-init`), and is therefore part of every phase's output path set. It references files as `../<path>`, which needs kustomize-controller's disabled load restrictor (Flux default, verify at the pinned version; fallback: plan 01 moves cluster manifests under `cluster-config/`). F11 checks `cluster-dir-closure` and `no-records-in-kustomize` (§22).
- Ingress mode is selected by `components: [../../components/ingress-tunnel]` or `ingress-direct` in `clusters/<c>/kustomization.yaml`, and the same component in `seed/kustomization.yaml` (F11 check `ingress-mode-consistency` against `cluster-vars.INGRESS_MODE`).

### 8.2 Component directory contract

`gitops/platform/<component>/base/kustomization.yaml` contains:
- `namespace: <component namespace>` (except cluster-scoped-only components);
- the chart source (`OCIRepository` or `HelmRepository`) in namespace `flux-system`, named `<component>`;
- `HelmRelease` `<component>` in the component namespace;
- `configMapGenerator` producing `<component>-values` from `values.yaml` (hash suffix enabled, so a value change triggers an upgrade);
- any standalone manifests (PVCs, CNPG `Cluster`, `Certificate`, `ServiceMonitor`, `PrometheusRule`, `NetworkPolicy` additions).

Overlays may patch replicas, resources, anti-affinity and storage replica counts only. Profile differences outside these fields require a note in the owning plan.

### 8.4 Root Kustomization and source indirection (ADR-0300)

Steady-state root (committed in `gotk-sync.yaml`):

```yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata: {name: flux-system, namespace: flux-system}
spec:
  interval: 10m
  retryInterval: 1m
  timeout: 5m
  sourceRef: {kind: GitRepository, name: flux-system}
  path: ./gitops/clusters/<cluster>
  prune: true
  wait: false            # root only applies layer objects; health is per layer
  decryption: {provider: sops, secretRef: {name: sops-age}}
  postBuild:
    substitute:
      SC_SOURCE_KIND: GitRepository
      SC_SOURCE_ROOT: "."
      SC_PROFILE: self-hosting-minimum
      SC_CLUSTER: <cluster>
---
apiVersion: source.toolkit.fluxcd.io/v1
kind: GitRepository
metadata: {name: flux-system, namespace: flux-system}
spec:
  interval: 1m
  timeout: 60s
  url: ssh://git@forgejo-ssh.forgejo.svc.cluster.local/strange-company/strange-company.git
  ref: {branch: main}
  secretRef: {name: flux-system}     # identity, identity.pub, known_hosts (SOPS, flux-source-auth.sops.yaml)
  ignore: |                          # identical to the seed Bucket's file set (SEED-18): only gitops/, no default exclusions
    /*
    !/gitops/
```

`spec.ignore` replaces Flux's default exclusion list, so the GitRepository artifact contains exactly the `gitops/` tree that the seed Bucket carries, and seed and steady renders see the same files (F11 check `source-ignore-parity` compares both `ignore` values with the Bucket template in plan 19 §7).

The seed root (created by `sc-bootstrap`, plan 19) differs only in three ways:
- `sourceRef: {kind: Bucket, name: flux-system}`;
- `path: ./<cluster>/<sha>/gitops/clusters/<cluster>/seed`;
- `SC_SOURCE_KIND: Bucket`, `SC_SOURCE_ROOT: ./<cluster>/<sha>` (`SC_PROFILE` and `SC_CLUSTER` are identical).

**Root substitution scope (SEED-4).** The root's `postBuild.substitute` runs over **every** object the root applies, not only the layer `sourceRef`/`path`. Therefore:
- every object in `gotk-components.yaml` carries `kustomize.toolkit.fluxcd.io/substitute: disabled` (added by `commonAnnotations` in `flux-system/kustomization.yaml`), because Flux CRD descriptions contain literal `${var:=default}` text;
- inside root-applied objects (the layer Kustomizations, including recovery-component `spec.patches` such as `serverName: <cluster>-g$${CNPG_FORGEJO_SOURCE_GEN}`), every variable other than the four root-only ones is written `$${VAR}`, which the root turns into `${VAR}` for the layer's own substitution (escape semantics verify at the pinned Flux; 19-AC-17 re-verifies with strict substitution on);
- F11 check `root-substitution-scope` renders the root with only the root-only variables defined and strict mode on, and fails if any unescaped non-root variable remains or if a `gotk-components` object lacks the annotation. The check runs on every committed cluster **and** on the fixture `ci-blackstart` (a `ci-shm-tunnel` copy with the plan 45 recovery components and a fixture `RecoveryRecord`), so the recovery overlay is rendered on every PR (DR-17).

The Bucket artifact keeps object keys including the prefix, which was verified in source-controller: `fetchIndexFiles` joins the full key under the artifact root. That is why `SC_SOURCE_ROOT` exists.

### 8.5 HelmRelease conventions

```yaml
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata: {name: <component>, namespace: <ns>}
spec:
  releaseName: <component>          # explicit, identical in seed and steady state
  targetNamespace: <ns>
  storageNamespace: <ns>
  interval: 30m
  timeout: 10m                      # 15m longhorn, 20m forgejo
  maxHistory: 5
  chartRef: {kind: OCIRepository, name: <component>, namespace: flux-system}   # preferred
  # or chart.spec: {chart: <name>, version: "<exact semver>", sourceRef: {kind: HelmRepository, name: <repo>, namespace: flux-system}}
  valuesFrom:
    - {kind: ConfigMap, name: <component>-values}
  install:
    crds: CreateReplace
    remediation: {retries: 3}
  upgrade:
    crds: CreateReplace
    cleanupOnFail: true
    remediation: {retries: 3, remediateLastFailure: true, strategy: rollback}  # class "controller"
  driftDetection: {mode: enabled}
  test: {enable: false}
```

Decisions:
- **Three remediation classes** (ADR-0304):
  - `controller` (cert-manager, CNPG operator, Traefik, cloudflared, kube-prometheus-stack, OTel, kured, Loki, Tempo): upgrade remediation `retries: 3, strategy: rollback`.
  - `controller-no-rollback` (Longhorn only, ADR-0201: Longhorn does not support downgrades): upgrade remediation `retries: 0, remediateLastFailure: false`. Upgrades go through `longhorn-upgrade-gate` and plan 48's one-minor-at-a-time rule.
  - `stateful-app` (Forgejo, Authentik, Woodpecker, Grafana, `strange-company`): upgrade remediation `retries: 0, remediateLastFailure: false`. An app that migrated its database schema must not be rolled back to an older image automatically. A failed upgrade stays failed, `SCFluxReconciliationFailing` fires, and plan 48's procedure decides.
  - The class is recorded as label `strange.company/remediation-class` on the HelmRelease, and F11 check `remediation-class` enforces the matching fields.
- **Install remediation `retries: 3` is safe for all**, because stateful apps never let the chart create their data PVCs. PVCs are standalone, prune-protected manifests (§8.6), so an uninstall remediation cannot delete data.
- **`test.enable: false`.** Helm test pods are frequently not PSA-restricted-compliant and add flakiness. Readiness is judged by `wait`, health expressions and the owning plan's gate checks.
- **`driftDetection: enabled`.** A component may use `mode: warn` only with an `ignore` justification in its plan, for example webhook `caBundle` injection by cert-manager (`ignore: [{paths: ["/webhooks/0/clientConfig/caBundle"], target: {kind: ValidatingWebhookConfiguration}}]`).
- **OCI charts:**
  - `OCIRepository.spec.ref.digest: sha256:...`, plus `ref.tag` recorded in a comment for humans.
  - `layerSelector: {mediaType: application/vnd.cncf.helm.chart.content.v1.tar+gzip, operation: copy}`.
  - `interval: 12h` (immutable digest).
  - Where upstream publishes cosign signatures, use `verify: {provider: cosign}` (plan 23 lists which).
- **HTTP Helm repositories:** `HelmRepository.spec.interval: 12h`, exact `version`.
- **CRDs** shipped by charts are kept on uninstall (e.g. cert-manager `crds.keep: true`). For CRDs applied as plain manifests, prune is disabled.

### 8.6 Prune semantics and protection (ADR-0304)

- All layers and the root use `prune: true`. Removing a manifest from Git deletes it from the cluster. That is the GitOps contract.
- **Protected kinds** must carry `metadata.annotations["kustomize.toolkit.fluxcd.io/prune"] = "disabled"`:
  - `Namespace`;
  - `PersistentVolumeClaim`;
  - `PersistentVolume` (statically declared PVs, e.g. Longhorn volumes bound by name, plan 13);
  - `longhorn.io/Volume` (plan 13, ADR-0201);
  - `postgresql.cnpg.io/Cluster`;
  - `barmancloud.cnpg.io/ObjectStore`;
  - `CustomResourceDefinition` (applied outside Helm);
  - `longhorn.io/BackupTarget`.

  F11 check `prune-protection` fails on any rendered object of a protected kind without it.
- **Accepted consequence:** deleting a protected object requires a human `kubectl delete` through break-glass (plan 15), after the manifest is removed from Git. Plan 49 (destroy) and plan 47 (remove node) document this.
- **PR check `gitops-destructive-diff`** (plan 52 schedules it): `sc-gitops diff --base origin/main --head HEAD` renders both revisions for every cluster and lists removed or renamed objects. The check fails if a removed object's kind is protected, or if a removed object is a `HelmRelease` of class `stateful-app`, unless the PR head commit carries the trailer `GitOps-Allow-Destroy: <kind>/<namespace>/<name>` for each one. The trailer is reviewed by the human merger.

### 8.6a Component `capsule-chart-sources` (CD-33, plan 45 §9.4; implemented at H04)

Used only by `./bootstrap recover --from-capsule` when GitHub-hosted chart repositories and GHCR may be unreachable. The recovery commit adds it to `clusters/<c>/kustomization.yaml` and `seed/kustomization.yaml` (both, so seed and steady renders stay identical; `seed-steady-identity` still applies).

- **Serving.** `recover` uploads the capsule's chart archives (verified against the signed `capsule.json`) to `s3://<prefix>-bootstrap-seed/<cluster>/capsule-charts/<capsule-id>/`, unpacked as one directory per chart `<name>-<version>/` (plain chart directories, so no packaged-archive path semantics are needed). The component declares `Bucket/capsule-charts` in `flux-system` (`provider: generic`, that prefix, `interval: 12h`) with Secret `capsule-charts-credentials`: a SOPS file in the recovery commit holding the read-only `seed-read` instance of `SC-OBJECT-STORAGE`. This Bucket is **not** the seed Bucket and is not deleted at T6. Images need no repointing: their digests are unchanged and the capsule image archives are pre-imported into containerd on every node (plan 45 §9.4), so pulls by digest resolve locally.
- **Repointing.** For each seed-set and restore-path layer (`cert-manager`, `cnpg`, `longhorn`, `traefik`, `cloudflared`, `forgejo`; Flux itself is applied from `gotk-components.yaml` and needs no chart), the component adds a Flux `spec.patches` entry on the layer Kustomization object that replaces the HelmRelease's `chartRef`/`chart.spec.sourceRef` with `chart.spec: {chart: ./<name>-<version>, sourceRef: {kind: Bucket, name: capsule-charts, namespace: flux-system}, reconcileStrategy: ChartVersion}`. `<version>` equals `versions/charts.lock.yaml`, so the rendered chart content is byte-identical to the upstream chart and the source switch at transfer changes nothing.
- **Removal.** A later reviewed PR removes the component once upstream sources are reachable. The chart source change causes one Helm upgrade per repointed release with identical manifests; for `stateful-app` releases (Forgejo) this is acceptable because the rendered output is identical (verified by `make gitops-diff`, which renders both revisions).

## 13. Security boundary

- **Trust:** Flux is fully trusted. It applies cluster-admin-equivalent changes, because kustomize-controller and helm-controller run with `cluster-admin` (upstream default). Its authority is bounded by **what is merged to `main` on Forgejo**, which is gated by branch protection (ADR-0019).
- **Read-only source:** the GitRepository uses a read-only deploy key (ADR-0016). Flux cannot push. F11 check `no-write-creds`: no `flux-system` manifest references a token-bearing Secret other than `flux-system`, `sops-age`, `seed-bucket-credentials`.
- **Inbound:** only Prometheus scraping (port 8080) and, optionally, notification-controller webhook receivers. No Receiver is configured in MVP; the 1m GitRepository polling makes them unnecessary. Nothing in `flux-system` is exposed through ingress (master plan §6.1).
- **Outbound:**
  - the Forgejo SSH Service;
  - the Kubernetes API;
  - the object-storage endpoint (seed only);
  - chart registries in `versions/platform.lock.yaml` (OCI/HTTPS 443);
  - Alertmanager (9093).
- **PSA:** `flux-system` is labeled `enforce: restricted`. Upstream Flux controllers run non-root with read-only rootfs and drop all capabilities (verify at implementation; fall back to `baseline` with justification in plan 37 if a controller is incompatible).
- **Workers and Hermes** have no NetworkPolicy path to `flux-system` [SPEC §88] (plan 36), and no RBAC on `*.toolkit.fluxcd.io` (plans 34, 37).
- **Tamper surface:** whoever can merge to `main` controls the cluster. This is the intended authority model [SPEC §4.9].

## 14. Happy path

1. A PR changes `gitops/`. CI runs F11 (`make gitops-validate`) and `gitops-destructive-diff`. A human merges.
2. Within ≤1m the GitRepository fetches `main@sha1:<new>`.
3. The root applies changed layer objects (if any). Each layer whose content changed reconciles in `dependsOn` order, and HelmReleases whose values ConfigMap hash or chart changed upgrade.
4. Every layer reports `Ready=True` with `status.lastAppliedRevision == main@sha1:<new>`. `gotk_resource_info{ready="True"}` follows.
5. Typical end-to-end latency from merge to applied is ≤ 3m for manifest-only changes and ≤ 15m for chart upgrades.

## 15. Failure modes

| Failure | Detection | Effect | Automated response | Procedure |
|---|---|---|---|---|
| Forgejo unreachable or deploy key rejected | GitRepository `Ready=False` (`SCFluxSourceFailing`) | No new changes applied; running state unaffected | source-controller retries every interval | `flux-reconciliation-failure.md` §A; `restore-forgejo.md` |
| Render error (bad kustomization, undefined var) | Kustomization `Ready=False` reason `BuildFailed` (`SCFluxReconciliationFailing`) | That layer and dependents not updated | retry every `retryInterval` | `flux-reconciliation-failure.md` §B (revert PR) |
| SOPS decryption failure (wrong recipient, missing `sops-age`) | reason `DecryptionFailed` | Layer stuck | retry | `flux-reconciliation-failure.md` §C; plan 35 `sops-decryption-failure.md` |
| Health check timeout | reason `HealthCheckFailed` | Dependents blocked by `dependsOn` | retry | §D |
| HelmRelease upgrade fails (`controller` class) | HR `Ready=False` | Rolled back automatically up to 3 times | rollback | §E |
| HelmRelease upgrade fails (`stateful-app` class) | HR `Ready=False`, `Stalled` | App may be partially upgraded; no automatic rollback | none (deliberate) | §E + plan 48 |
| Drift (manual `kubectl edit`) | helm-controller drift detection event; KSM shows no change | Corrected on the next HR reconcile (≤30m) | correction | none; investigate actor via audit log |
| Accidental removal of stateful manifest from Git | `gitops-destructive-diff` PR check; if merged, object stays (prune disabled) | No data loss | prune skipped | §F |
| Object stuck terminating (finalizer) | Kustomization `HealthCheckFailed` / prune timeout | Layer not Ready | none | §G |
| Flux controller crashloop / OOM | `SCFluxControllerDown` | Nothing reconciles | kubelet restart | §H |
| Flux upgrade breaks a CRD API version | Layers fail with `no matches for kind` | Reconciliation halted | none | §I (revert Flux bump PR; plan 48) |
| Suspended object forgotten | `SCFluxSuspendedTooLong` after 2h | Drift accumulates | none | §J |
| Bucket source still present after transfer | `SCFluxSeedSourcePresent` | Seed not finished | none | `failed-flux-handoff.md` |

## 16. Retry behavior

- Sources retry on `interval` (GitRepository 1m).
- Kustomizations retry on `retryInterval: 2m` after a failure and reconcile on `interval: 10m` otherwise.
- HelmReleases follow their remediation class (§8.5). After retries are exhausted, helm-controller stops until the spec changes or an operator runs `flux reconcile helmrelease <name> -n <ns> --force` (procedure).
- `dependsOn` waits are re-queued every `--requeue-dependency=15s`.
- Nothing retries indefinitely at high frequency. A permanently failing layer costs one render every 2 minutes, which is bounded.

## 17. Idempotency behavior

- Flux apply is server-side apply with field manager `kustomize-controller`. Re-applying identical content is a no-op: no resourceVersion change for unchanged objects.
- `make gitops-flux-regen` is deterministic. Running it twice yields no diff (18-AC-3).
- `sc-gitops render` is a pure function of the Git tree, `versions/platform.lock.yaml` and the chart cache, keyed by digest. Its output is byte-stable (sorted objects, sorted keys).

## 18. Bootstrap behavior

Plan 19 owns the sequence. This plan guarantees:
- the seed path `gitops/clusters/<c>/seed` is a **strict subset** of the steady path, through `profiles/<p>/seed`;
- the seed path includes `flux-system/gotk-components.yaml` (Flux self-manages from the first reconcile) and `gotk-sync.yaml`'s `GitRepository` (it exists, not Ready, until Forgejo serves the repo), but deletes the root `Kustomization` object through a kustomize `$patch: delete`. This prevents the Bucket-sourced root from overwriting itself with the Git-sourced definition before transfer.

## 19. Upgrade behavior

**Flux self-upgrade:**
1. Renovate (or a human) bumps `flux.version` in `versions/platform.lock.yaml`.
2. CI runs `make gitops-flux-regen` and fails if the committed `gotk-components.yaml` differs. The PR must therefore include the regenerated file.
3. F11 check `flux-upgrade-isolation`: a PR that changes `gotk-components.yaml` may change nothing else under `gitops/` except `flux-system/` patches. This keeps rollback trivial.
4. Before merge, `sc-gitops validate` runs against the new CRD schemas. If a used API version (e.g. `helm.toolkit.fluxcd.io/v2beta2`) is removed in the new version, the PR must first migrate manifests in a separate PR. F11 check `flux-api-versions` uses the CRD `served` versions.
5. After merge, the root applies the new controllers. kustomize-controller replaces itself, which upstream supports. Verify: all controllers `Ready` and `flux version` reports the new version (procedure in plan 48).

**Component upgrades** go through chart version or digest bumps (Renovate PRs, plan 23), F11, merge, and HelmRelease upgrade under the remediation class. Plan 48 owns sequencing (e.g. CNPG operator before PostgreSQL minor; Longhorn one minor at a time).

## 20. Recovery behavior

- Flux state is rebuilt by seeding again (plan 19 black-start variant; plan 45).
- With a live cluster and broken Flux:
  - re-apply controllers with `./bootstrap exec -- sh -c 'sc-gitops render --cluster <c> --flux-system --exclude-sops | kubectl apply --server-side --field-manager=kubectl --force-conflicts -f -'` (the rendered `flux-system/` kustomization without the SOPS-encrypted `flux-source-auth.sops.yaml`, which would otherwise be applied as ciphertext; SEED-16);
  - re-apply the root from `gotk-sync.yaml` (procedure `flux-reconciliation-failure.md` §H).
- Inventories are reconstructed from Git on the next successful reconcile. Prune-protected objects are never deleted by a recovery.
- Loss of `sops-age` is a rotation scenario: re-create it from the recovery bundle (plan 35, `rotate-age-key.md`).

## 22. Testing strategy

All of these are deterministic, offline after the chart and schema cache fill, and make no model calls.

| Target | What | Where |
|---|---|---|
| `make gitops-validate` (F11) | The full offline gate below | PR, main (plan 52) |
| `make gitops-flux-regen-check` | Regenerate `gotk-components.yaml` for every cluster dir; `git diff --exit-code` | PR |
| `make gitops-diff` | Destructive-diff check (§8.6) | PR |
| `go test ./src/internal/gitops/...` | Unit tests of the render emulation (substitution, SOPS stripping, ordering), each check with positive and negative fixtures under `src/internal/gitops/testdata/` | PR |
| k3d handoff test | plan 19 | main, nightly |

**`sc-gitops validate` checks.** It runs for each committed cluster dir: `ci-shm-tunnel`, `ci-sha-direct`, `ci-handoff`, `ci-blackstart` (recovery overlay fixture, plan 45 content), and every real `clusters/<c>` present. It runs in both modes: **seed** (Bucket-substituted) and **steady**.

1. `render`: build root content using the same Kustomize/envsubst libraries kustomize-controller uses (`github.com/fluxcd/pkg/kustomize`, pinned to the Flux version's `go.mod`). Then build each layer path with root-level substitution, then layer-level substitution from `cluster-vars` (fixture values for CI clusters). SOPS files: the `sops` metadata is stripped and `ENC[...]` values are replaced with `"sops-placeholder"` (never decrypted in CI).
2. `helm-render`:
   - for every HelmRelease, pull the chart by pinned digest/version into `~/.cache/sc/charts/<digest>` (network only to registries listed in `versions/platform.lock.yaml`);
   - merge values in helm-controller order (`valuesFrom` in order, then inline `values`);
   - run `helm template --kube-version <k3s version> --api-versions <from rendered CRDs> --include-crds`. Chart `values.schema.json` is enforced by `helm template` where present.
   - **Verify** that the merge order matches helm-controller at the pinned version (18-AC-12).
3. `kubeconform -strict -summary -kubernetes-version <k3s> -schema-location default -schema-location <cache>/crd-schemas/{{.Group}}/{{.ResourceKind}}_{{.ResourceAPIVersion}}.json`. The CRD schemas are generated from the pinned CRDs: Flux, cert-manager, CNPG, barman plugin, Longhorn, Traefik, prometheus-operator, and any chart-bundled CRDs. The generator is `openapi2jsonschema` logic inside `sc-gitops`. Missing schema means failure (no `-ignore-missing-schemas`).
4. `no-bitnami` (CD-26, which supersedes CD-20; SI-31): failure on (a) any rendered image reference from a Bitnami registry or repository (`docker.io/bitnami/*`, `bitnamilegacy`, `registry-1.docker.io/bitnami*`, `*.bitnami.com`), (b) any `HelmRepository`/`OCIRepository` whose URL points at a Bitnami repository or registry (`charts.bitnami.com`, `oci://registry-1.docker.io/bitnamicharts`, any path containing `bitnamicharts`), and (c) any chart dependency in a pulled chart's `Chart.yaml`/`Chart.lock` (recursively) whose `repository` points at such a location, unless that dependency is **vendored inside the upstream chart package** (present under its `charts/`, so nothing is fetched from Bitnami) **and** its own `Chart.yaml` has `type: library`. A vendored Bitnami subchart of any other type, or a Bitnami chart deployed as a component, fails.
5. `images-pinned`: every `image:` in rendered Pods/templates (including init and ephemeral containers, and CRD-embedded images known to the checker: CNPG `imageName`, Longhorn images in settings) matches `@sha256:[0-9a-f]{64}$`.
6. `charts-pinned`: every `OCIRepository` has `ref.digest`. Every HelmRelease `chart.spec.version` is exact semver. No `HelmRepository` of `type: default` points at a non-HTTPS URL.
7. `namespaces`: the set of rendered `Namespace` objects equals master plan §5 (minus `kube-system`), including `ci-build` and `monitoring-node` (CD-13). Each has `pod-security.kubernetes.io/{enforce,audit,warn}` at the level in §5, plus `strange.company/tier`. Every namespaced object targets a namespace in that set.
8. `gitops-file-modes` (no executable files or symlinks under `gitops/`, so that the seed artifact tree hash is reproducible, plan 19 §8.3), `prune-protection`, `remediation-class`, `seed-closure`, `seed-chart-source`, `layers-only-kustomizations`, `root-vars-scope`, `no-secret-substitution`, `profile-consistency`, `ingress-mode-consistency`, `no-write-creds`, `flux-api-versions`, `flux-upgrade-isolation`, `git-chart-source-allowlist`, `no-flux-generated-netpol`, `cluster-vars-schema` (§8–§9).
9. `seed-steady-identity` (18-R-2): for every layer in the seed set, the seed-mode rendering and the steady-mode rendering of the layer's *content* are byte-identical. For the layer object itself, the difference is limited to `spec.sourceRef.kind` and the `spec.path` prefix.
10. Generated-file freshness: `public-hosts-generated` (`sc-gitops gen public-hosts --check`, plan 09) and `policy-configmaps-fresh` (`sc-gitops policy-configmaps --check`: the committed `sc-policy` and `sc-company-context` ConfigMaps equal a regeneration from `policy/**` and `context/company/*.md`, every key decodes to an existing path, total size ≤ 921600 bytes; plan 54).
11. `no-estop-configmap` (plan 33, ADR-0452): no rendered manifest of any cluster, layer or chart contains a `ConfigMap` named `sc-emergency-stop`, so Flux can never adopt or prune the operator-created emergency-stop object.
12. Cluster directory (SEED-1): `cluster-dir-closure` (`cluster-config/kustomization.yaml` equals `sc-gitops gen cluster-config --check`; every Kubernetes manifest under the cluster dir is reachable from exactly one of the root or `cluster-config`; every namespaced object it applies targets a namespace rendered by the `namespaces` layer, which `cluster-config` depends on) and `no-records-in-kustomize` (no kustomization references a file whose `apiVersion` is `strange.company/*`, and no file under `secrets/offcluster/`).
13. `root-substitution-scope` (SEED-4, §8.4), including the `ci-blackstart` fixture.
14. `single-owner` (SEED-5): across the root, every layer and every `helm template` output, each (group, kind, namespace, name) appears exactly once, except the explicitly listed `strange.company/adopt: <owner>` pairs (none in MVP).
15. Seed-set safety: `seed-credential-phase` (SEED-22) and `seed-no-internal-images` (STO-1: no seed layer image under `git.${BASE_DOMAIN}/`).
16. `source-ignore-parity` (SEED-18) and `no-insecure-tls` (AUTH-14: no `insecureSkipVerify`, `tls_skip_verify_insecure`, `SKIP_TLS_VERIFY`, `noTLSVerify` in rendered manifests or values).
17. `triplet-size-consistency` (plan 13, STO-19): for every stable-named Longhorn triplet, PVC request == PV capacity == `Volume.spec.size`.
18. `ci-egress-mode` (plan 36): fails if `SC_CI_EGRESS=direct` in a cluster whose `runner.enabled` is true, **except** when the HEAD commit carries the trailer `SC-Emergency-Merge: <incident-id>` (plan 55 `emergency-merge.md`; GC-02, NC-2).
19. `capsule-chart-sources` (CD-33): `ci-blackstart` is also rendered with the component enabled (fixture capsule chart directories in `test/fixtures/capsule-charts/`). Every seed-set and restore-path HelmRelease must resolve its chart from `Bucket/capsule-charts` at exactly the `versions/charts.lock.yaml` version; the rendered manifests of those releases must be byte-identical to the upstream-sourced render; no other HelmRelease may be patched; and without the component no object may reference `capsule-charts`.

Output: JUnit XML at `out/gitops/junit.xml` and a human summary. The exit code is non-zero on any failure.
