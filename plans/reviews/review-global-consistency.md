## 2. Verdict

**FAIL** for this area. The DAG is acyclic as written, but it does not describe what the gates actually require:

- Three gate-level cycles exist (P07↔P09, P09↔P10, P07↔C08).
- About 20 hidden edges exist.
- The H phase depends on the C phase in practice, although the DAG says otherwise.

That is exactly the SPEC §132 item 43 failure mode. Separately, two runtime cycles (the merge gate versus its own components, and egress-proxy versus CI) have no workable documented break path. Most other findings are fixable editorial or contract work. The substrate plans (07, 08, 09, 36, 51, 52) are strong.

## 4. Circular-dependency analysis

### 4.1 Static DAG (`plans/dag.yaml`)

The graph is acyclic and every dependency resolves. **It is not faithful to the gates.** GC-01 lists three gate-level cycles: P07↔P09 (Grafana/Prometheus ACs in plan 15), P09↔P10 (39-AC-4 backups dashboard), and P07↔C08 (15-AC-14 Hermes). It also lists about 20 missing hard edges. The H phase is declared independent of the C phase but its ACs need the Runner, Hermes and the e-stop. After the GC-01 fixes (move ACs, add edges) the graph stays acyclic. I checked that each proposed edge goes from a later node to an earlier one in the current topological order, or between unordered siblings.

### 4.2 Runtime and bootstrap cycles

| Pair | Finding |
|---|---|
| Forgejo ↔ Authentik | **No cycle.** Forgejo starts with local accounts. SSO arrives at P07. Break-glass and machine tokens work with Authentik at 0 replicas (15-AC-23). Authentik's config is delivered by Flux from Forgejo, but its runtime does not need Forgejo. |
| Woodpecker ↔ Forgejo ↔ Runner | **Cycle at the merge gate (GC-02).** Woodpecker needs Forgejo (OAuth, clone, hooks), and `sc-ci-config` needs the Runner only for verify intents. From C09, every merge needs Runner-posted statuses, and every merge needs CI. A broken Runner, Woodpecker or `sc-ci-config` blocks its own fix. A break exists implicitly (`forge apply --stage bootstrap`), but the procedures are contradictory or unworkable. |
| egress-proxy ↔ chart ↔ CI | **Cycle (GC-02, GC-04).** From C02, CI fetches through the proxy. A broken proxy release stops CI, so the revert cannot get CI green, and the F11 `ci-egress-mode` check forbids falling back to `direct`. Bootstrap ordering is fine: the image is built at P11 in direct mode and deployed at C01, and Q-36-02 accepts this. But plan 23 states the opposite for `ci-build` (GC-04). |
| Woodpecker ↔ trusted images (`sc-ci-config`, `sc-release`) | **Broken correctly.** GHCR bootstrap images come from the interim lane and are digest-pinned by reviewed PRs (plan 23 §14 steps 1–3). |
| Kubelet image pulls ↔ public edge ↔ Forgejo | **Hidden dependency (GC-05).** Internal images need Forgejo *and* the Cloudflare edge in tunnel mode, including during black start and reschedules. |
| Flux ↔ Forgejo | **Broken correctly.** Source-controller keeps its last artifact. `failed-flux-handoff.md` §F (`seed --emergency-source`) restores reconciliation from GitHub or the Bucket while Forgejo is repaired. NetworkPolicy mistakes that block Flux have a direct `kubectl apply` break-glass (plan 36 §20). |
| Monitoring ↔ alerts ↔ notifications | **No cycle.** Alertmanager is the hub. Prometheus, Alertmanager or egress down → Watchdog stops → external heartbeat (42-R-6). The Runner's post-failure alert travels through Prometheus, not through the Runner. Absence of a heartbeat is itself an always-notify alert. Defects (GC-03, GC-12, GC-18) are wiring, not cycles. |
| Heavy-slot advertiser ↔ CI | **Weak cycle.** If the advertiser is broken, step pods cannot schedule, so CI cannot merge a fix. Plan 51 §20's manual `create job --from=cronjob` reuses the broken CronJob. Covered by the GC-02 emergency-merge procedure, plus a documented `kubectl patch node … --subresource=status` from the toolbox. |
| Runner ↔ Gateway | **No cycle.** The Gateway waits for Runner-run migrations (CD-04) and reads the JWKS ConfigMap. The Runner only reads Gateway status. |
| Expansion ↔ merges | **No cycle.** Expand PRs need human merges and CI. Runner dispatch is paused but the Runner keeps running, so statuses are still posted. |
