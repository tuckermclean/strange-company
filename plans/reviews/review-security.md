## 2. Verdict

**PASS WITH FIXES.** Blocking findings: 0. Major: 11. Minor: 14.

The security design is unusually thorough. It has an explicit threat model, a defense-in-depth layer table, 27 CEL policies with stable codes, a 46-case escape matrix, a 63-class secret register whose schema forces creator, consumer, storage, rotation and recovery, two-tier SOPS, an egress proxy and an explicit residual-risk register. None of the findings below needs a SPEC change or an architectural reversal. Several are still significant:
- The release trust chain can be **triggered or tapped from places the threat model says cannot reach it**: worker-pushable refs (SEC-1), Pod specs readable by many identities (SEC-3), and the cluster age key that upstream operators can read (SEC-4).
- One admission failure mode **can brick the whole cluster**, and the brick blocks its own repair (SEC-6).
- The SPEC §105 "bypass network policy" test **misses pod-to-node traffic**, which the host firewall does not restrict (SEC-5).

All majors must be fixed before the DAG nodes named in each row are implemented (mostly F12, P08, P11 and C02).

## 4. Circular-dependency analysis

DAG (`plans/dag.yaml`, security-relevant nodes F12, P08, P11, C01, C02, C09, P12): **no graph cycle**. P11 → C01 (the Runner image is signed by trusted CI), C02 → F12, and the bootstrap trust P08–P11 runs from digest-pinned GHCR interim images (23 §13, §18). The plugin image never signs itself in the same run. These are acyclic.

Runtime and bootstrap ordering cycles found:
1. **Admission parameters vs cluster-wide bindings (SEC-6).** A binding with `parameterNotFoundAction: Deny` that matches `*/*` cluster-wide also matches Flux's CREATE of its own parameter ConfigMap in `flux-system`. If the ConfigMap is absent while the binding is active (first apply ordering inside one Flux layer, a rename, a prune, or recovery), Flux cannot recreate it, and nothing else can mutate the cluster either. Breaking the cycle requires break-glass deletion of the binding. Fix: parameters in an earlier layer, plus parameter-free identity policies (SEC-6).
2. **Egress proxy ↔ CI merge gate ↔ egress-proxy release.** From C02, `ci-jobs` and `ci-build` reach registries only through `egress-proxy`. If a proxy release (or `policy/egress.yaml`) breaks it, three things stop: the revert PR's `ci/woodpecker/pr/ci` cannot download modules (merge blocked for non-admins); a fixed image cannot be built (the build lane needs the proxy); and F11 `ci-egress-mode` rejects the escape hatch `SC_CI_EGRESS=direct` while `runner.enabled`. `agent-runner-failure.md` §H says "fix by PR", which cannot pass CI. Fix: the procedure uses a break-glass admin merge, or Flux applies a revert of the digest-bump commit. Allow `SC_CI_EGRESS=direct` with an explicit `emergency: <incident>` annotation that raises a critical alert.
3. **Forgejo registry ↔ trusted CI after black start.** `sc-ci-config`, `sc-release` and the Runner images live in the Forgejo registry from P11 on. CI therefore cannot run until Forgejo (including registry blobs in S3 `forgejo-objects`) is restored. Plan 45 orders Forgejo first and the toolbox has a GHCR fallback, so this is **not** a deadlock. Plan 45 should state explicitly that the GHCR interim `sc-ci-config` digest is the fallback if `forgejo-objects` is lost.
4. **Signing-key rotation.** The new key must be on `main` before anything it signs is promoted, and promotion uses base-revision keys. This is sequential (signing-key-rotation safety check 3), not cyclic.
5. **Release lane and worker refs (SEC-1).** Not a cycle, but an ordering hazard: the Runner's ref audit, the only control if Forgejo protection is not enforced for deploy keys, runs *after* the pipelines that the rogue ref triggers.

## 5. SPEC contradictions / false assumptions for `plans/spec-issues.md`

- **SI-06 may be partly false in the other direction.** Forgejo glob branch protection with rule priority could restrict deploy-key pushes to `agent/**` *preventively* (SEC-2). Re-verify on the pinned Forgejo. If it works, SPEC §87's "SHOULD only push `agent/*`" becomes enforceable and ADR-0007 should switch from detection to prevention.
- **SPEC §88 / §105 "bypass network policy" vs data exfiltration (interpretation).** With DNS and "necessary package/source registries" allowed (several of them writable), network policy cannot prevent exfiltration of the repository a worker legitimately holds. §105 should be read as "cannot reach unapproved *services*", and confidentiality of repository content rests on R-9/R-10 acceptance. Record this so that "bypass network policy" is not later read as "cannot exfiltrate".
- **SPEC §37 "Stochastic workers SHALL not receive release-signing keys" (underspecified).** Read literally, it is satisfied even if a worker can *cause* the release pipeline to sign worker-authored content (SEC-1). Record the stronger interpretation that plans 23/34 must meet: no worker-controlled ref or content can reach a signing step.
- **SPEC §85 / §98 implicit assumption (false assumption).** Namespacing plus RBAC does not isolate Kubernetes Secrets from upstream platform operators: cert-manager, CNPG, Longhorn and Flux hold cluster-wide Secret read. The in-cluster SOPS key is therefore exposed to every such operator (SEC-4). Not a SPEC change; record it so that plans do not claim otherwise.
