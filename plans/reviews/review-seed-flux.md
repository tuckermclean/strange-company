## 2. Verdict

**FAIL.** The Bucket-source design (ADR-0005/0300) is sound and clearly better than helm-install-then-adopt. The integrity check, the T0–T8 switch, the rollback concept and the C1–C8 mapping are well thought out. However, two design holes would deadlock a fresh seed:

- **SEED-1:** how cluster-directory Secrets and ConfigMaps reach the cluster is undefined, and the only described path deadlocks on namespace ordering.
- **SEED-2:** the Forgejo upgrade-gate Job has no API egress and insufficient RBAC.

Several major gaps also weaken the "no duplicate-resource chaos" proof:

- No single-owner guarantee.
- The root inventory is not compared.
- Root-level substitution can corrupt the objects the root applies.
- The integration test as specified cannot pass and would not prove the property if it did.

## 4. Circular-dependency analysis

**DAG (`plans/dag.yaml`):** P04 → {P03, F11, F12}; P05 → P04; P06 → P05; P07/P08 → P06; P12 → P07–P11. There are no cycles. Plan 19's code (seed and handoff packages) has no separate F-node, but it is reachable through P04, which is acceptable.

**Runtime and bootstrap ordering:**

| Potential cycle | Status |
|---|---|

## 5. SPEC contradictions or false assumptions for `plans/spec-issues.md`

- **New SI (Interpretation/Cost-risk), SPEC §29 + §88 + §18:** "S3-compatible object storage" may sit on a private network or a non-443 port, especially with the `existing` provider. Node DNS upstreams may also be private. The platform's "Internet egress excludes private ranges" rule (plan 36) then blocks the seed. Proposed resolution: endpoint-derived egress components (SEED-3), plus a preflight check that rejects or flags unsupported endpoint placements.
- **SI-05** already records the SPEC §112 deviation (identity restored after Flux bootstrap). That is fine; plan 19 §18.2/§18.3 should cite SI-05 explicitly.
- No contradiction within SPEC §34/§35 itself. The plans' interpretation (SI-04, ADR-0005) is a legitimate and stronger realization, once the findings above are fixed.
